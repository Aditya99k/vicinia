01 · orientation

Why any of this infra exists

Before Eureka, Config Server, or the gateway existed, "the backend" was going to be 16 independent Spring Boot applications. None of them know each other's address, none of them share configuration, and a browser can't sanely be pointed at 16 different hostnames. Stage 1 builds the three pieces of connective tissue that turn 16 separate jars into one coherent system.

discovery-server
The phone book. Every service registers itself here on boot and asks it "where is X right now?" instead of hardcoding an address.
config-server
The shared settings file. Instead of baking config into each service's jar, services fetch it over HTTP at startup.
api-gateway
The front door. The only service a client ever talks to directly; it forwards each request to the right place behind the scenes.
02 · discovery-server

Service discovery — Eureka

The problem Eureka solves: if order-service needs to call inventory-service, what address does it use? A hardcoded http://192.168.1.14:8084 breaks the moment that instance restarts on a different port, moves to a different machine, or you scale to three instances of it. Eureka replaces "a fixed address" with "ask the registry, right now, who's alive."

2.1Registration & heartbeats

Every service that wants to be found is a Eureka client. On startup it sends the registry one POST: "I am AUTH-SERVICE, I live at this host and port." From then on it sends a small heartbeat (a "renewal") every 30 seconds to say "still alive." If the registry doesn't hear a renewal within a 90-second lease, it assumes the instance is dead and evicts it from the registry.

2.2Self-preservation mode

Eureka has a safety switch: if it suddenly sees renewals drop across many instances at once, that usually means the registry's own network is having a bad moment — not that every instance actually died. Self-preservation mode stops evicting in that scenario and keeps serving the (possibly stale) registry it already has, on the theory that a stale answer is safer than telling every client "nothing exists."

We disabled it locally (enable-self-preservation: false) on purpose — it's a dev-speed choice, not a production one. Without it, restarting a service you're actively working on gets evicted in ~5 seconds instead of possibly lingering as a dead entry for up to 90.

2.3Client-side load balancing

Once there are multiple instances of a service registered, who picks which one handles a given call? Eureka itself doesn't — it just hands back the list. Spring Cloud LoadBalancer, running inside the calling service (or the gateway), picks one instance from that list, by default round-robin. This is "client-side" load balancing: no separate load-balancer process sits in the middle, the caller decides.

2.4Our actual config, line by line

discovery-server/src/main/resources/application.yml

# port the registry itself listens on
server:
  port: 8761

eureka:
  client:
    # the registry doesn't register with itself or fetch its own list
    register-with-eureka: false
    fetch-registry: false
  server:
    # dev-speed tradeoff — see 2.2 above
    enable-self-preservation: false
    eviction-interval-timer-in-ms: 5000
Why register-with-eureka: false?

The discovery-server annotates itself with @EnableEurekaServer, which turns it into the registry — it isn't also trying to be a client of itself. Every other service in the system will have this flag left at its default (true).

03 · config-server

Centralized configuration

The problem Config Server solves: with 16 services, "change one property" shouldn't mean "rebuild and redeploy one jar." Centralizing config also means there's exactly one place to see what's configured for the whole system, instead of 16 scattered application.yml files.

3.1The contract

Config Server exposes a simple REST contract: GET /{application}/{profile} returns a merged property set for that service and profile. "Merged" means layered, in a specific precedence — the most specific file wins:

3.2Backend types

native
Reads files straight off a filesystem or classpath folder. Simplest possible setup, no extra moving part — what we used for the zero-cost single-VM deploy.
git
Clones an actual git repo; label maps to a branch or tag, so config gets full version history and rollback for free.
vault
Backed by HashiCorp Vault — for secrets specifically, not general config.

We chose native deliberately: one less service to run and secure, at the cost of no built-in change history. Worth revisiting if config ever needs an audit trail.

3.3How a client actually pulls it

A consuming service declares this once, and the fetch happens automatically before the rest of its own startup finishes:

spring:
  config:
    import: optional:configserver:http://localhost:8888

The optional: prefix matters: without it, the service refuses to start if config-server is unreachable. With it, a missing config-server just means "start with whatever's bundled locally" — the right default while config-server itself is still young infra, not yet holding anything a service can't run without.

3.4The bug we actually hit

Gotcha — classpath resolution

We first put the shared config in config-server/config-repo/application.yml — a folder sitting next to src/. Config Server was set to search-locations: classpath:/config-repo, and it came back empty. Why: Maven only puts src/main/resources/ (and its subfolders) onto the compiled classpath. A sibling folder next to src is invisible to the running jar, no matter how correct its contents are. Moving it to src/main/resources/config-repo/application.yml fixed it immediately — same file, same content, different location relative to what actually ships.

This is a useful general lesson, not just a one-off fix: any classpath: reference in Spring config only ever sees what Maven/Gradle actually packages under the resources root.

04 · api-gateway

The single front door

With 16 backend services, a client (a browser, a mobile app) cannot reasonably be pointed at 16 different hostnames — and shouldn't be, since that also means auth, rate limiting, and logging would need to be reimplemented 16 times. The gateway is the one service every external client talks to; it decides where each request actually goes.

4.1Three building blocks

Route
One rule: an id, a destination uri, the predicates that must match, and any filters to apply.
Predicate
A condition on the incoming request — Path=/api/auth/**, a header, a method. All predicates on a route must match for it to apply.
Filter
Modifies the request or response — strip a path prefix, add a header, apply a circuit breaker or rate limiter. Stage 1 has none yet; Stage 2 adds a JWT filter, Stage 15 adds resilience filters.

4.2The lb:// scheme

Our routes point at lb://AUTH-SERVICE, not a real host. lb tells the gateway "don't treat this as a literal address — ask the load balancer." At request time, the load balancer asks Eureka for live AUTH-SERVICE instances, picks one (§2.3), and the gateway proxies the request to that instance's real host:port. This is exactly why a route can be written before the service behind it exists: until AUTH-SERVICE registers, that route simply has nothing to resolve to, and returns a 503.

4.3Why reactive/non-blocking matters here specifically

Spring Cloud Gateway runs on Spring WebFlux over Netty — event-loop, non-blocking I/O — rather than the traditional one-thread-per-request servlet model. That matters uniquely for a gateway: it sits in the hot path of every single request in the system and spends most of its time waiting on a downstream service to respond. A thread-per-request model would tie up an OS thread for each in-flight wait; the event loop model handles thousands of concurrent in-flight requests on a handful of threads instead.

4.4Our route table (excerpt) & the public-paths list

api-gateway/src/main/resources/application.yml

spring:
  cloud:
    gateway:
      routes:
        - id: auth-service
          uri: lb://AUTH-SERVICE
          predicates:
            - Path=/api/auth/**
        - id: catalog-service
          uri: lb://CATALOG-SERVICE
          predicates:
            - Path=/api/catalog/**

# not enforced yet — Stage 2's JWT filter reads this list
vicinia:
  gateway:
    public-paths:
      - /api/auth/login
      - /api/catalog/**

Deciding the public-paths list now, before the auth filter exists, is deliberate: it's the contract Stage 2 builds against, rather than a decision made under pressure while wiring JWT validation.

05 · docker-compose.infra.yml

Docker & Docker Compose

Postgres, Redis, and Redpanda don't run as Java processes — they run as containers, defined once in docker-compose.infra.yml and brought up together with a single command.

5.1Container vs. image vs. VM

Image
A read-only template — filesystem layers plus metadata (what command to run, what ports to expose). Pulled from a registry like Docker Hub, or built from a Dockerfile.
Container
A running instance of an image, with its own writable layer on top. You can run many containers from one image.
vs. a VM
A container shares the host machine's kernel and isolates at the process/filesystem level; a VM virtualizes hardware and boots a full separate OS. Containers start in milliseconds precisely because there's no OS to boot.

5.2Compose file anatomy, using our actual services

docker-compose.infra.yml — postgres service

services:
  postgres:
    image: postgres:16-alpine
    # keeps the container running across a host reboot / crash
    restart: unless-stopped
    environment:
      POSTGRES_USER: vicinia
      POSTGRES_PASSWORD: vicinia
    ports:
      - "5432:5432"  # host:container
    volumes:
      # named volume — data outlives container recreation
      - vicinia-postgres-data:/var/lib/postgresql/data
      # bind mount — runs once against an empty data dir, see 5.3
      - ./backend/docker/postgres-init:/docker-entrypoint-initdb.d
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U vicinia"]
      interval: 5s
ports: "5432:5432"
Left side is your Mac's port, right side is the port inside the container. They don't have to match — we kept them equal for clarity.
Named volume
Docker-managed storage that persists even if the container is deleted and recreated — this is where Postgres's actual data lives, outside the container's disposable filesystem.
healthcheck
"Container started" ≠ "Postgres is accepting connections yet." Other tooling (and a human reading docker compose ps) can wait for healthy, not just running.

5.3The Postgres init-script mechanism

The official Postgres image runs every .sql/.sh file found in /docker-entrypoint-initdb.d/ — but only once, only the very first time it starts against a truly empty data directory. That's why 001-create-databases.sql created all 9 logical databases on first boot. It also means: editing that file later and re-running docker compose up does nothing, because the volume is no longer empty. A change there only takes effect after docker compose down -v (which deletes the volume too).

5.4Redpanda's networking flags

This pair looks redundant but solves a real problem:

--kafka-addr=PLAINTEXT://0.0.0.0:9092
--advertise-kafka-addr=PLAINTEXT://redpanda:9092

kafka-addr is what the broker binds to inside its own container. advertise-kafka-addr is the address the broker tells connecting clients to use for all future requests — and that has to be redpanda:9092 (the container's service name), because that's the only address other containers on the same Docker network can actually reach. If it advertised localhost, every other container would try to connect to itself and fail. This exact bind-vs-advertise split shows up in real Kafka, Redis Cluster, and most clustered systems — worth recognizing on sight.

06 · putting it together

A day in the life of a request

Two different sequences, both worth being able to narrate: what happens at boot, and what happens per request once a real domain service exists behind the gateway.

6.1Boot order

  • discovery-server starts first — nothing depends on it being populated, it just needs to be reachable.
  • config-server starts — reads config-repo/ off its own classpath, doesn't need discovery-server yet.
  • api-gateway starts — pulls shared config from config-server (optional), then registers itself with discovery-server.
  • Any future domain service repeats the gateway's pattern: pull config, then register.

6.2Per-request flow (once AUTH-SERVICE exists)

  • Client calls POST /api/auth/login on the gateway's public address.
  • Gateway matches the Path=/api/auth/** predicate → route auth-service.
  • Gateway's load balancer asks the Eureka client for live AUTH-SERVICE instances, picks one.
  • Gateway proxies the request to that instance's real host:port; the response flows back through the gateway to the client.

Notice discovery-server and config-server never sit in the request's hot path — both only matter at boot (or on a config refresh). That's intentional: the fewer services a live request depends on, the fewer ways it can fail.
