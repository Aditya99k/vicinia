01 · fundamentals

Why split into microservices at all

The alternative — one big Spring Boot app with everything in it — is simpler to build. Vicinia deliberately doesn't do that. Understanding why is the single most important thing to be able to explain.

A monolith is one deployable unit: one codebase, one build, one process, usually one database. Everything can call everything else with a plain Java method call. A microservices architecture splits that into many small, independently deployable services, each owning its own slice of the domain and — critically — its own database. Services talk to each other only over the network (HTTP or messages), never by sharing a database table or importing each other's internal classes.

The trade you're making: you give up the simplicity of a single process and a single transaction that spans everything, in exchange for independent deployability (ship order-service without touching catalog-service), independent scaling (scale inventory-service under checkout load without scaling review-service), and fault isolation (a bug that crashes notification-service doesn't take down checkout).

The honest cost, worth saying out loud in an interview

Microservices don't remove complexity — they move it. A single-process monolith gets ACID transactions for free; a microservices system has to solve "how do I keep data consistent across services" itself, by hand, which is exactly why this project needed the Saga pattern (§4) and idempotent consumers (§3) at all. If you're asked "why not just a monolith," the honest answer is: at Vicinia's actual scale, a monolith would have been simpler — this project chose microservices deliberately, as a learning and portfolio exercise in the patterns a real system at scale needs, not because the traffic demanded it.

1.1Vicinia's own split

16 independently deployable services (plus a shared common library, not itself deployed): 3 platform services (service discovery, config, gateway) and 13 domain services, each owning one noun in the system — auth, user, merchant, catalog, inventory, cart, coupon, payment, order, delivery, notification, review, settlement. See §10 for the full table.

02 · fundamentals

Event-driven architecture & Kafka, from scratch

The problem: when a customer places an order, at least five services need to know something happened — cart needs to clear, merchant needs a task created, inventory already reserved, payment needs to resolve, settlement eventually needs to pay the merchant. How do those five services find out, without order-service calling all five synchronously and becoming a single point of failure for every one of them?

Two ways to tell another service something happened: synchronous (a direct REST call — "call me now, wait for my answer") or asynchronous (publish a message to a broker, anyone interested subscribes and reacts whenever they're ready). Vicinia uses REST for request-response needs (order-service asking inventory-service "do you have stock, right now, yes or no") and Kafka for fan-out notification needs (order-service announcing "this order is confirmed," with no idea or care who's listening).

2.1Kafka concepts, in order

Broker
The server that stores and routes messages. Vicinia runs Redpanda instead of real Apache Kafka — same wire protocol, same client library, no code difference, but a single binary with no separate Zookeeper process and a far smaller memory footprint (a deliberate choice for fitting on a free-tier VM — see §18).
Topic
A named stream of messages, e.g. order-events. Producers publish to a topic; consumers subscribe to one.
Partition
A topic is split into ordered partitions for parallelism. Vicinia publishes keyed by orderId, so every event for the same order lands on the same partition — guaranteeing they're processed in the order they were published, without needing every service to coordinate on ordering.
Consumer group
A named set of consumer instances sharing the work of one topic. Two services both reading order-events are two separate consumer groups (each sees every message); two instances of the same service reading the same topic are the same group (they split the partitions between them).
Offset
A per-partition, per-group bookmark: "I've processed up to message #N." This is what lets a crashed consumer resume where it left off instead of reprocessing everything or skipping ahead.
A real bug this exact model caused, and its fix

Two @KafkaListener methods in the same service both reading the same topic with the same groupId split that topic's partitions between them — for a single-partition topic, only one of the two ever gets messages, the other sits permanently idle, silently. This was caught twice in this project: once as a JSON-deserialization mismatch (Spring Kafka's spring.json.value.default.type is a per-service global setting, not per-listener — reusing a class name across two intended-different event shapes broke deserialization), and once caught before it shipped, when a new "cancelled" handler was about to be added as a second @KafkaListener on a topic a first one already consumed. The fix both times: one listener per (topic, service) pair, branching internally on an eventType field via a switch statement, never two listeners on the same topic in the same service.

2.2The envelope shape

Every event on every topic uses the same wrapper, so any consumer can deserialize the envelope first and only then decide (via eventType) what payload shape to expect inside it:

// EventEnvelope — every message on every topic looks like this
{
  "eventId": "uuid",        // unique per publish, useful for tracing/dedup
  "eventType": "order.confirmed",
  "schemaVersion": 1,
  "occurredAt": "2026-08-27T10:00:00Z",
  "payload": { "...whatever this event type carries..." }
}

One topic per aggregate (order-events, payment-events, delivery-events, merchant-events, inventory-events, product-events) rather than one topic per event type — see §14 for the full topic map and who publishes/consumes each.

03 · fundamentals

Idempotency

An operation is idempotent if doing it twice has the same effect as doing it once. This matters enormously in an async, at-least-once-delivery system: Kafka (and most message brokers) can redeliver a message — after a consumer crash mid-processing, after a rebalance, after a retry — so every consumer has to assume "this exact message might arrive more than once" and behave correctly anyway.

3.1Three real idempotency techniques used in this codebase

Existence check
merchant-service's order-confirmed handler checks taskRepository.findByOrderId(orderId).isPresent() before creating a task — a redelivered order.confirmed event is a safe no-op, not a duplicate task.
State-guarded transition
completeFromDelivery and cancelFromOrderEvent both only act "while the task is still READY" — a redelivered event that arrives after the state already moved on does nothing, rather than throwing or double-applying.
Atomic conditional update
The strongest guarantee, covered fully in §5 — a single SQL UPDATE ... WHERE status = 'expected' that the database itself either applies exactly once or rejects, no matter how many times or how concurrently it's attempted.

Why does at-least-once delivery exist at all — why not just guarantee exactly-once?

Because guaranteeing a message is delivered and processed exactly once, end to end, across a network that can fail at any point, is provably impossible to do for free (it's a variant of the Two Generals problem). Real systems pick at-least-once delivery (never lose a message, occasionally redeliver one) and push the responsibility for handling duplicates onto the consumer — which is exactly why idempotent consumers are a load-bearing design requirement, not an optional nicety.

04 · fundamentals

The Saga pattern & compensating transactions

A single checkout touches inventory, payment, and (eventually) delivery and settlement — four separate databases, owned by four separate services. A classic ACID transaction can't span them. A Saga is the answer: a sequence of local transactions, each in one service, where every step that changes state has a matching compensating action that undoes it if a later step fails.

4.1Choreography vs. orchestration

There are two ways to coordinate a Saga: orchestration (one central coordinator service explicitly tells every other service what to do, in order) and choreography (no coordinator — every service reacts to events and publishes its own, and the overall flow emerges from those reactions). Vicinia is choreographed: order-service never tells merchant-service "now create a task" — it publishes order.confirmed, and merchant-service's own consumer decides to react to it. The trade-off: choreography has no single place to read "the whole flow," but no single point of failure either.

4.2The 7 real compensation triggers in this codebase

Every one of these releases the inventory reservation and/or publishes order.cancelled (which triggers an event-driven refund in payment-service), tagged by a Prometheus counter (order.compensation, tag trigger) so a Grafana panel can show exactly which failure mode is happening in production, not just a raw "cancelled" total:

TriggerWhat happened
coupon_rejectedCoupon service rejected the code at checkout (expired, usage limit hit)
insufficient_stockInventory reservation failed — someone else got there first
wallet_payment_failedSynchronous wallet debit came back insufficient/failed
razorpay_payment_failedAsync webhook reported payment.failed
merchant_rejectedMerchant declined the order after payment succeeded
customer_cancelledCustomer cancelled pre-delivery
merchant_cancelled_readyMerchant's own escape hatch — no rider ever collected a ready order
05 · fundamentals

Concurrency, race conditions & the atomic conditional update

The single highest-leverage pattern to be able to explain fluently — it appears 5 separate times in this codebase, solving what looks like 5 different problems but is actually the same problem every time.

5.1The race, concretely

Two customers both try to buy the last unit of a product at the same instant. The naive approach — read the current stock, check if stock > 0 in application code, then write the decremented value — has a window between the read and the write where both requests can read "stock = 1," both decide it's available, and both write "stock = 0." Result: oversold, two customers charged for one unit.

The fix: let the database do the check-and-set atomically

Instead of "read, decide in Java, write," issue one SQL statement that does the check and the write as a single atomic operation the database itself guarantees can't be interleaved: UPDATE listings SET available_stock = available_stock - 1 WHERE id = ? AND available_stock >= 1. If two requests race, the database's own row-level locking serializes them — exactly one UPDATE actually changes a row (returns "1 row affected"), the other's WHERE clause no longer matches (returns "0 rows affected"). The application code just checks the affected-row count to know which one it was — no explicit lock, no synchronized block, no distributed lock service needed.

5.2The same shape, 5 places

Inventory reservation
inventory-service — the canonical example above. Verified under real load: 20 parallel reservation requests against a listing with stock=1, exactly one 201, nineteen 409s, final state availableStock=0, exactly one reservation row.
Coupon usage limit
coupon-service — UPDATE coupons SET usage_count = usage_count + 1 WHERE id = ? AND usage_count < usage_limit. Verified two ways: 20 parallel applies with distinct orderIds against usageLimit=1 → exactly one succeeds; separately, 15 parallel applies with the same orderId (a genuine double-submit) → all 15 return success but usage_count only nets +1 — idempotency under real concurrency, not just sequential retries.
Wallet balance
payment-service — pay and refund both conditionally update balance, never a blind read-then-write.
Razorpay webhook resolution
A webhook can be delivered more than once (Razorpay's own retry policy) — tryResolve conditionally transitions a payment from PAYMENT_PENDING, so a replayed webhook is a verified no-op, confirmed by replaying an identical delivery and checking the topic's offset didn't advance a second time.
Order status transitions
Every status change goes through OrderStatusTransition.assertAllowed(from, to) — not concurrency-atomic in the same SQL sense, but the same underlying principle: never trust that the in-memory object still reflects reality, always assert the precondition explicitly before acting.

Why not just use a distributed lock (e.g. a Redis lock) instead?

A lock adds a whole new failure mode: what happens if the process holding the lock crashes before releasing it? Now you need lock timeouts, fencing tokens, and a plan for "the lock expired but the original holder is still running." A conditional UPDATE has none of that — the database's own transaction guarantee is the lock, scoped automatically to exactly the row in question, released automatically the instant the statement completes. Simpler, and there's no separate system (Redis) that becomes a new single point of failure for correctness.

06 · fundamentals

JWT authentication, RBAC & Redis-backed blacklisting

6.1Why "stateless" auth, and what that word actually means

A traditional session-based login stores session state server-side (in memory or a shared store), and the browser just holds an opaque session ID cookie that points at it — every request needs a lookup. A JWT (JSON Web Token) instead packs the actual claims (user ID, roles, permissions, expiry) into the token itself, cryptographically signed so a server can verify it wasn't tampered with without looking anything up — the token is the credential. "Stateless" means any service holding the shared signing secret can validate any token, independently, with zero shared server-side session state.

// what's actually inside a Vicinia access token, decoded
{
  "jti": "uuid",           // unique token ID — the key the blacklist uses
  "sub": "user-uuid",
  "email": "...",
  "roles": ["CUSTOMER"],
  "permissions": ["ORDER_PLACE", "ORDER_VIEW_OWN"],
  "iat": 1787743893, "exp": 1787744793  // 15 min lifetime
}

6.2RBAC: roles vs. permissions

A role (CUSTOMER, MERCHANT, DELIVERY_PARTNER, ADMIN) is a coarse label a user has. A permission (ORDER_PLACE, CATALOG_MANAGE, STORE_MANAGE, DELIVERY_MANAGE, ...) is a fine-grained capability a role grants. Every protected endpoint checks a permission, never a role directly — the indirection means adding a new role, or changing what an existing role can do, is a data change (which permissions map to which role), not a code change in every controller that happens to care.

6.3How the gateway enforces this for every downstream service, for free

The API Gateway validates the JWT onceX-User-Id, X-User-Email, X-User-Roles, X-User-Permissions. Every downstream service just reads those headers — it never parses a JWT itself, and it never needs to, because it structurally can't be reached except through the gateway (an InternalRequestFilter on every service checks a shared internal secret the gateway alone stamps on every proxied request, rejecting anything that bypasses it).

6.4Redis-backed logout blacklisting

A JWT's whole value proposition is that no server-side lookup is needed to validate it — which creates an obvious problem: how do you invalidate one before it naturally expires (a logout, a stolen token)? The answer isn't to stop being stateless everywhere; it's one small, targeted stateful check, right at the edge:

// TokenBlacklistService — auth-service
public void blacklist(String jti, Instant expiresAt) {
    // TTL capped to the token's own remaining lifetime — the
    // blacklist entry expires from Redis at the exact moment the
    // token itself would have expired anyway, never outliving it
    long ttlSeconds = Math.max(1, Duration.between(Instant.now(), expiresAt).getSeconds());
    redis.opsForValue().set("blacklist:" + jti, "1", Duration.ofSeconds(ttlSeconds));
}

The gateway checks Redis.hasKey("blacklist:" + jti) on every authenticated request, before trusting the token further. This is the one place the system trades pure statelessness for a real security guarantee — and it's deliberately the smallest possible stateful surface: one Redis key lookup, not a full session store.

If checking Redis on every request adds a lookup, haven't you just reinvented sessions?

Not quite — the difference is what's being looked up. A session store holds the entire auth state (who is this, what can they do) and every request needs it. This blacklist check answers exactly one boolean question ("has this specific token been explicitly revoked?") and everything else — identity, roles, permissions — still comes from the token itself, verified by signature alone, with zero lookup. The stateful part is a targeted exception, not the whole mechanism.

6.5BCrypt

Passwords are never stored in plaintext or with a fast general-purpose hash (MD5, SHA-256) — those are designed to be fast, which is exactly the wrong property for a password hash (fast means an attacker with a stolen hash database can brute-force billions of guesses per second). BCrypt is deliberately slow and has a tunable work factor, and it automatically salts each hash (two users with the same password get different stored hashes), defeating rainbow-table attacks. One Spring Security bean (BCryptPasswordEncoder) covers both signup and password reset.

07 · fundamentals

Circuit breakers, bulkheads & retry — and why they're different tools

All three answer "a downstream call is failing or slow — what do I do about it," but at different points in the failure's lifecycle, and Vicinia deliberately uses two different libraries for them, not one.

Retry
A single call failed — try again, on the assumption the failure was transient (a network blip, a momentary timeout). Vicinia uses Spring Retry (@Retryable) for this, on InventoryClient and PaymentClient's outbound calls.
Circuit breaker
Retrying a call to a service that's genuinely down, not just transiently blipping, wastes time and keeps piling load onto something already struggling. A circuit breaker tracks the failure rate over a rolling window and "opens" (stops even attempting the call, fails fast instead) once failures cross a threshold — then periodically lets a few calls through ("half-open") to check if the downstream has recovered.
Bulkhead
Named after a ship's watertight compartments — limits how many concurrent calls to one specific downstream can be in flight at once, so a slow/hanging third-party doesn't exhaust the entire request-handling thread pool and take down calls to every other, unrelated service too.

7.1Where this is actually configured — and where it deliberately isn't

Resilience4j (circuit breaker + bulkhead) is configured in exactly one place: order-service's call out to payment-service for the Razorpay path specifically — not every inter-service call in the system.

# order-service/application.yml
resilience4j:
  circuitbreaker:
    instances:
      razorpay:                        # named instance — scoped, not global
        sliding-window-size: 10
        minimum-number-of-calls: 5
        failure-rate-threshold: 50     # % failures to trip open
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3
  bulkhead:
    instances:
      razorpay:
        max-concurrent-calls: 10
        max-wait-duration: 0           # fail fast once full, don't queue
A precise claim worth getting right

It would be easy to say "we used Resilience4j for retries and circuit breaking across the system" — that overstates it. Resilience4j here is specifically the third-party payment gateway's circuit breaker and bulkhead; retries elsewhere in the codebase are Spring Retry, a different library. Being able to draw this exact line — which library, which one call path, why scoped that narrowly — reads as far stronger in an interview than a vague "we added resilience patterns" claim, because it shows you understand why a third-party payment gateway specifically deserves this treatment and an internal, already-reliable service call doesn't need the same ceremony.

Why does only the payment gateway get a circuit breaker, and not, say, the call to inventory-service?

inventory-service is our own service, on the same network, with its own retry and well-understood failure modes — a slow inventory call is diagnosable and fixable directly. Razorpay is a third-party we have zero control over; if it degrades, the only thing we can control is how gracefully our system degrades in response — failing fast (circuit open) and not letting a hanging payment call monopolize threads (bulkhead) that other, unrelated requests need. Resilience engineering effort goes where the actual risk and the actual lack of control are highest, not applied uniformly everywhere for its own sake.

08 · fundamentals

Redis, beyond "a cache"

Redis is an in-memory key-value store — fast because it's RAM, not disk, and single-threaded-per-shard so operations are naturally free of the exact race conditions §5 worries about at the database layer. Vicinia uses it for four genuinely different jobs, which is itself worth being able to enumerate:

Cart storage
cart-service — a cart is inherently ephemeral, session-like data; a 7-day TTL on the key means an abandoned cart just evaporates, no cleanup job needed.
JWT blacklist
§6.4 — one key per revoked token, TTL-bound to the token's own expiry.
Rate limiting
Spring Cloud Gateway's built-in RequestRateLimiter, backed by RedisRateLimiter — a genuine token-bucket algorithm implemented as a Lua script executed atomically inside Redis, keyed per-user (by the same trusted X-User-Id header the gateway itself stamps) or per-IP for unauthenticated routes.
Delivery partner GEO search
delivery-service uses Redis's native GEOADD/GEOSEARCH commands to find online riders within a radius of a pickup point — a purpose-built geospatial index, not something bolted on top of a plain key-value store.
Note — a related but separate geo-search

Don't confuse the Redis GEO search above (finding a rider near a pickup point) with merchant discovery (finding a store near a customer) — that one is plain Haversine distance computed in application code against Postgres-stored coordinates, covered in §18. Two different problems that happen to both be "find something nearby," solved with two different tools for good reasons — worth being able to explain why they're not the same code path if asked.

09 · fundamentals

Observability: metrics, dashboards, and knowing something broke before a user tells you

Micrometer is a vendor-neutral metrics facade built into Spring Boot Actuator; point it at Prometheus (one dependency, near-zero config) and every service exposes a /actuator/prometheus endpoint in Prometheus's plain-text exposition format. Prometheus itself is a time-series database that pulls (scrapes) those endpoints on an interval and stores the history. Grafana queries Prometheus and renders it as dashboards.

9.1Two kinds of metrics, and why both matter

Infrastructure metrics
Request latency, JVM memory, Kafka consumer lag, dead-letter-topic volume — "is the system healthy as a piece of software." Mostly free from Spring Boot Actuator's auto-configuration.
Business metrics
Custom counters/gauges Vicinia added deliberately: order.funnel (created → payment success → merchant acceptance → delivered, tagged by stage), order.compensation (tagged by trigger — §4.2), order.stale.ready_for_pickup (a gauge — how many orders have sat waiting too long for a rider), inventory.oversell (a canary counter that should always read zero — if it's ever nonzero, the atomic-update guarantee in §5 failed), payment.outcome (tagged by method and outcome).

6 Grafana dashboards, one roughly per metric family above, plus a Kafka consumer-lag dashboard. The business metrics are the more interesting story in an interview: they're not something Actuator gives you for free, they're a deliberate choice about what's worth watching in this specific domain — a canary metric that should always be zero is a particularly strong thing to be able to explain, because it demonstrates thinking about how you'd notice your own concurrency guarantee silently breaking in production, not just that you built the guarantee once.

The 16-service map

Full table with ports and datastores lives in §22 for reference. The shape worth remembering: 3 platform services, 9 Postgres-backed domain services, 3 MongoDB-backed domain services, 1 Redis-primary domain service.

Why does each service get its own database instead of sharing one?

Database-per-service is what actually makes it a microservice, not just a separately-deployed process. If two services shared a database, they'd be coupled at the schema level — one service's migration could break the other, and you'd lose the ability to reason about a service's data invariants in isolation. Sharing infrastructure (all 9 Postgres-backed services running on one physical Postgres instance, per §18's cost-conscious deployment) is fine and doesn't violate this — what matters is that each service owns its own logical database and nothing else ever touches its tables directly.

11 · architecture

How a request actually flows

  1. Browser sends a request to api-gateway (the only service with a public port) with a Bearer JWT.
  2. Gateway's AuthGlobalFilter validates the signature and expiry, checks the Redis blacklist (§6.4), and — for CORS preflight (OPTIONS) requests — short-circuits before any of that, answered directly by Spring's CORS filter.
  3. Gateway strips any client-supplied X-User-* headers (never trust what the client sent) and stamps its own, verified ones.
  4. Gateway looks up which service owns this path via Eureka (service discovery — every service registers itself on boot, deregisters on shutdown) and load-balances the request there.
  5. The downstream service's own InternalRequestFilter checks a shared internal secret the gateway always stamps — a direct request to a service's own port, bypassing the gateway, is rejected with 403 even with a perfectly valid JWT, since that header is missing.
  6. The service handles the request, possibly calling other services synchronously (REST, for request-response needs) and/or publishing events to Kafka (for fan-out needs), then responds.
A real timing bug this flow caused

Spring Cloud Gateway's load-balancer keeps its own client-side cache of "which instances exist for this service," refreshed on its own schedule — separate from Eureka's own registry, which can already be correct while the gateway's cache hasn't caught up yet. Right after a fresh service starts, a request routed through the gateway can get a 503 even though the target service is healthy and Eureka-registered — seen live in this project's own CI. The fix wasn't to route around the gateway; it was to make the caller tolerant of a brief, bounded warm-up window (retry specifically on 503, a few times, with a short backoff) — the same "don't treat a startup race as a permanent failure" reasoning used elsewhere in the project.

The order lifecycle, end to end — the flagship whiteboard story

If an interviewer asks you to draw one thing, draw this. It touches nearly every pattern in this guide in one continuous story.

13 · architecture

Data ownership: why Postgres and MongoDB and Redis

Polyglot persistence — choosing the datastore per service based on that service's own access pattern, not standardizing on one database for the whole system.

Postgres — 9 services
Strongly relational, transactional data with real invariants to enforce (an order's line items, a coupon's usage count, a wallet balance) — exactly where ACID guarantees and the conditional-update pattern (§5) matter most.
MongoDB — catalog, review, notification
Catalog's product documents vary in shape by category and don't need relational joins; notifications and reviews are high write-volume, read-by-recipient/product data with no cross-entity transactional requirement.
Redis — cart, plus cross-cutting concerns
Ephemeral or genuinely different-shaped data (§8) that doesn't belong in a relational schema at all.

One deliberate, documented deviation worth mentioning if asked: in production, Postgres is self-hosted (one instance, 9 logical databases) rather than using a managed free-tier database service — because managed free tiers typically autosuspend on inactivity, and a multi-second cold start on the first request after idle is a real latency problem when a single checkout makes synchronous calls to 3+ services in sequence. MongoDB stays on a managed free tier (Atlas) instead, because only 3 services need it and a managed tier has no downside there.

Retry & dead-letter topics

Every consumer is wrapped in @RetryableTopic — a failed message gets retried a few times with backoff on an auto-created -retry topic, then lands on a -dlt (dead letter topic) for manual inspection rather than blocking the partition forever or silently dropping. Suffixes are service-qualified (e.g. order-events-merchant-service-retry, not just order-events-retry) specifically because multiple services consume the same topic — an unqualified suffix would collide.

Customer journey

Signup/login → browse (city or, now, real-distance-based store discovery, §18) → product detail → cart (single-merchant-per-cart, enforced server-side) → checkout (wallet, Razorpay, or COD) → live order tracking → rate a delivered item → wallet top-up → manage addresses (now requiring a captured location, not just typed text) → notifications.

Merchant journey

Apply (with document metadata) → admin review → onboarding → set store hours/location → go live → appear in /nearby → receive orders in a live queue → accept/reject → mark ready → the queue keeps showing the order (with its live pickup/delivery substatus, mirrored from order-service, not a static label) until the rider actually delivers it, not until the merchant's own last click → cancel if no rider ever shows → settlement/payout history, with real item-level detail per entry, not a bare total.

Cross-cutting: geo search, Cloudinary, and the deployment pipeline

18.1Real distance-based store discovery

A genuine bug, found from a live user report: a customer with a valid default address saw zero nearby stores. Root cause — store discovery matched on the city string, exactly (case-insensitively), and every seeded merchant's city field said "Bangalore" or "Bengaluru" — two spellings of the same city, neither matching the customer's own typed city text. The fix replaced string matching with real geometry:

// GeoDistance.java — Haversine great-circle distance
public static double km(double lat1, double lon1, double lat2, double lon2) {
    double dLat = Math.toRadians(lat2 - lat1);
    double dLon = Math.toRadians(lon2 - lon1);
    double a = Math.sin(dLat/2)*Math.sin(dLat/2)
            + Math.cos(Math.toRadians(lat1))*Math.cos(Math.toRadians(lat2))*Math.sin(dLon/2)*Math.sin(dLon/2);
    return EARTH_RADIUS_KM * 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1-a));
}

A merchant now shows up for a customer only if the real distance between their coordinates is within that merchant's own advertised delivery radius, sorted nearest-first — city text is now only a fallback for an address saved before location capture was made mandatory. Verified live against real seeded coordinates, not just unit-tested in isolation.

18.2Cloudinary signed uploads

Merchant product photos upload directly from the browser to Cloudinary — the bytes never pass through Vicinia's own backend at all. The backend's only job is minting a short-lived HMAC-SHA1 signature over the sorted upload parameters plus the account's secret (Cloudinary's own documented algorithm) — proof that this specific upload request is authorized, without the backend ever touching the image itself.

18.3The deployment pipeline

One shared, parameterized Dockerfile (a build arg selects which of the 16 services to build) rather than 16 near-duplicate files — multi-stage: a Maven build stage compiling just the target module plus the shared common library, then an Alpine-JRE runtime stage with a fixed -Xmx160m -XX:+UseSerialGC heap, sized against a documented RAM budget for running all 16 services plus self-hosted Postgres/Redis/Redpanda on one free-tier VM. GitHub Actions builds and pushes all 16 images to GHCR on every green CI run, gated by workflow_run so a broken test suite never reaches a deploy step.

A real, previously-invisible bug this surfaced

None of the 16 services actually had spring-boot-maven-plugin activated in their own pom.xml — only present in the parent POM's pluginManagement, which sets a default but doesn't apply it. mvn package had silently produced a non-executable plain JAR this entire project, invisible until now because local development exclusively used mvn spring-boot:run, which runs from the compiled classpath and never needed a repackaged jar at all. Found only because Dockerizing forced an actual mvn package + java -jar for the first time.

20 · interview prep

Question bank

Why Kafka/Redpanda instead of just calling other services with REST everywhere?

Fan-out and decoupling. If order-service had to synchronously call cart-service, merchant-service, and settlement-service directly on every order, it would become a single point of failure for all three, and adding a fourth interested service later would mean editing order-service's code. With events, order-service publishes once, knows nothing about who's listening, and a new consumer can be added with zero changes to the publisher.

What happens if a Kafka consumer crashes mid-processing?

Its offset for that message was never committed, so on restart (or on another instance in the same consumer group picking up its partition) the message is redelivered — which is exactly why every consumer has to be idempotent (§3). This is the concrete mechanism behind "at-least-once delivery."

Single point of failure in this architecture?

The API Gateway (every request passes through it) and Eureka (if the registry is down, the gateway can't resolve new service instances, though already-cached routes keep working briefly). Both are real, worth naming unprompted rather than waiting to be caught not knowing — a good system-design answer names its own weak points.

Why does the gateway strip client-supplied X-User-* headers instead of trusting them?

Because those headers are exactly what downstream services use to make authorization decisions — if a client could set X-User-Roles: ADMIN directly on a request to a downstream service, the entire RBAC system would be bypassable. The gateway is the only thing allowed to set them, and it does so only after independently validating the JWT itself.

How would you scale this system if traffic grew 100x?

Each service already scales independently (that's the whole point of the split) — add more instances of the hot path services (order, inventory, payment) behind Eureka, no code change needed. The harder problems: the single self-hosted Postgres instance becomes a bottleneck (would need read replicas or eventually splitting the busiest services onto their own Postgres instances), and Redpanda's single-node setup (fine for a free-tier VM, not for real production throughput) would need a real multi-broker cluster.

Why choose to self-host Postgres/Redis/Redpanda in production instead of managed services?

A specific, considered tradeoff, not "cheaper is always better": managed free tiers commonly autosuspend on inactivity (cold-start latency is a real problem for a system doing multiple synchronous cross-service calls per checkout), and self-hosting on one already-provisioned free-tier VM has zero incremental cost. It's a decision made after evaluating the actual failure mode a managed free tier would introduce, not a default.

21 · interview prep

Traps to avoid — claims that sound good but don't survive one follow-up question

"Transactional outbox"
Don't say this. There's no outbox table or relay process in this codebase — events are published as a separate step after the DB commit completes, which is simpler but doesn't give the same atomicity guarantee a real outbox pattern provides (a crash between commit and publish would lose the event). If asked "what happens if the process crashes right after the DB commit but before the Kafka publish," the honest answer is: the event is lost, and that's a known, accepted gap, not something the current design solves.
"OTP-based authentication"
Don't say this. There's no OTP flow anywhere in this codebase. Don't confuse it with the real HMAC-SHA256 usage, which verifies Razorpay's webhook signatures — a different mechanism, for a different purpose.
"Resilience4j retry policies across services"
Resilience4j here is circuit breaker + bulkhead, scoped to one call path (Razorpay). General inter-service retry is Spring Retry, a separate library. Getting this backwards under questioning is an easy, avoidable stumble.
"Redis-backed rate limiting" / "caching" / "blacklisting" as one vague clause
These are three genuinely different Redis usages (§8) — be ready to explain each independently, not as one interchangeable blob.
Implying this handles real production traffic/scale
It's a portfolio project, single free-tier VM, no load testing performed. Own that plainly — pivot to design reasoning (§ scaling question above) rather than implying numbers that were never measured.
"Live in production" / "processing real payments"
Razorpay integration is test-mode. The engineering (real API calls, real signed webhooks, real signature verification in both directions) is genuine — the money movement is not. Say exactly that if asked.
"Automated tests cover the Saga"
They don't — see the trap note in §19's bullet 5. Compensation was verified manually during development, not by an automated test suite.

Glossary

Choreography
Coordinating a multi-service flow via each service independently reacting to events, with no central coordinator (§4.1).
Compensating transaction
The "undo" step of a Saga — reversing a prior local transaction's effect (§4).
Consumer group
A named set of consumers sharing a topic's partitions (§2.1).
DLT / DLQ
Dead letter topic/queue — where a message lands after exhausting its retry attempts, for manual inspection.
Idempotent
Safe to apply more than once with the same effect as applying it once (§3).
JTI
JWT ID — a unique identifier embedded in a token, used as the blacklist's key.
RBAC
Role-Based Access Control — authorizing via roles that grant permissions (§6.2).
Saga
A sequence of local transactions across services, each with a compensating action (§4).
