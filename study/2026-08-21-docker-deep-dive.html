01 · fundamentals

Containers vs. virtual machines, from zero

The problem both solve: "run this software reliably, regardless of what's already installed on the machine it lands on." They solve it very differently.

A virtual machine emulates an entire computer — virtual CPU, virtual disk, virtual network card — and boots a complete, separate operating system on top of that fake hardware. Three VMs on one laptop means three full operating systems running simultaneously, each with its own kernel, each using gigabytes of disk and needing a minute or more to boot.

A container doesn't emulate hardware or boot a separate OS at all. It shares the host machine's existing kernel, and uses two Linux kernel features — namespaces (make a process think it's the only thing running, with its own filesystem/network/process-list view) and cgroups (limit how much CPU/memory it can use) — to create the illusion of isolation without the cost of a separate OS. Three containers on one machine share one kernel, start in a couple of seconds, and each typically uses megabytes, not gigabytes.

On a Mac specifically

Docker containers need a Linux kernel underneath them, and macOS's kernel (Darwin) isn't Linux. That's exactly why Docker Desktop exists as an app on Mac: it quietly runs one lightweight Linux virtual machine in the background, and every container you run actually runs inside that one VM, sharing its kernel. This is also why start-infra.sh has to open -a Docker and wait for it — "Docker" on Mac genuinely means "boot that background Linux VM first."

02 · fundamentals

Images, layers, and containers

Three words that get used almost interchangeably in casual conversation, but mean precisely different things.

Image
A read-only template — a filesystem plus metadata (what command to run, what ports it expects) — either pulled pre-built from a registry like Docker Hub, or built locally from a Dockerfile.
Dockerfile
A text file of instructions (FROM, COPY, RUN, ...) that describes how to build an image, step by step.
Layer
Each Dockerfile instruction produces one immutable, cacheable layer. An image is really just a stack of these layers.
Container
A running instance of an image, with one thin writable layer added on top for anything the running process changes.

Layers are why Docker builds are usually fast on the second try: if only your source code changed, Docker reuses every cached layer up to the first instruction that actually changed, and only rebuilds from there down. This is also why Dockerfiles conventionally put rarely-changing steps (installing dependencies) before frequently-changing ones (copying your own source code) — so an edit to your code doesn't invalidate the expensive dependency-install layer.

Where Vicinia stands right now

We haven't written a Dockerfile yet. docker-compose.infra.yml only pulls pre-built images (Postgres, Redis, Redpanda, their consoles) — none of our own Java code is containerized yet. Every Spring Boot service still runs directly on the host via mvn spring-boot:run (see start-infra.sh). Writing a Dockerfile per service is Stage 19 — see §10.

03 · fundamentals

The Docker toolchain — four names, four different things

Docker Engine
The background daemon (dockerd) that actually builds images and runs/stops/networks containers. The real worker.
Docker Desktop
The Mac/Windows app. Bundles the Engine, the lightweight Linux VM (see §1's callout), and a GUI dashboard. This is what open -a Docker launches.
Docker CLI
The docker command-line tool. Doesn't do the work itself — it sends instructions to the Engine and shows you the results.
Docker Compose
A CLI plugin (docker compose ...) for describing and running a multi-container setup from one YAML file, instead of one long docker run command per container. Covered next.
04 · fundamentals

Docker Compose — orchestrating many containers as one

Vicinia's infra is 5 containers (Postgres, Redis, Redis Commander, Redpanda, Redpanda Console). Running each by hand means 5 long, easy-to-typo docker run commands, re-typed identically every single time. Compose replaces that with one declarative file.

# generic shape — not our actual file yet, see §5 for that
services:
  my-service:
    image: some-image:tag
    ports:
      - "hostPort:containerPort"
    environment:
      KEY: value
    volumes:
      - named-volume:/path/in/container
    healthcheck:
      test: ["CMD", "some-check-command"]

volumes:
  named-volume:

docker compose -f docker-compose.infra.yml up -d reads this file and starts everything defined in it, in the background (-d = detached). docker compose down stops and removes the containers again. Compose also automatically creates one private network shared by every service in the file — covered in §6.

How Vicinia actually uses Docker

The real file, service by service — docker-compose.infra.yml at the repo root.

5.1postgres

postgres:
  image: postgres:16-alpine
  restart: unless-stopped
  environment:
    POSTGRES_USER: vicinia
    POSTGRES_PASSWORD: vicinia
    POSTGRES_DB: vicinia
  ports:
    - "5432:5432"
  volumes:
    - vicinia-postgres-data:/var/lib/postgresql/data
    - ./backend/docker/postgres-init:/docker-entrypoint-initdb.d
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U vicinia"]

The official Postgres image, when it starts against a genuinely empty data directory, runs every .sql/.sh file it finds mounted at /docker-entrypoint-initdb.d/ — exactly once. That bind mount is how our own 001-create-databases.sql (committed to the repo, see §7) creates the 9 logical databases on first boot.

5.2redis

redis:
  image: redis:7-alpine
  ports:
    - "6379:6379"
  volumes:
    - vicinia-redis-data:/data
  healthcheck:
    test: ["CMD", "redis-cli", "ping"]

Stock Redis, nothing project-specific here — cart, OTP, refresh tokens, the access-token blacklist, and rate limiting all share this one instance, differentiated only by key prefix (see docs/ARCHITECTURE.md §13).

5.3redis-commander

redis-commander:
  image: rediscommander/redis-commander:latest
  environment:
    REDIS_HOSTS: local:redis:6379
  ports:
    - "9191:8081"
  depends_on:
    - redis

A small web UI for browsing Redis keys, at localhost:9191. Notice its REDIS_HOSTS value: redis:6379, not localhost:6379 — from inside this container, redis is the hostname of the other container, not itself. That's the subject of §6.

5.4redpanda & redpanda-console

The Kafka-protocol broker and its web UI. This is the most configuration-heavy service in the file — it's covered in full depth (every flag explained) in study/2026-08-20-infra-fundamentals.html §5.4, and the one real bug it caused is walked through in §9 of this doc.

06 · this project

Networking — how containers find each other, and how you reach them

Compose creates one private network per project (vicinia_default) and attaches every service to it. Inside that network, each service's own name is its hostname — that's why redis-commander can reach Redis at literally the address redis:6379, no IP address needed, no configuration beyond "use this name." Docker runs an internal DNS that resolves service names to whichever container is currently running that service.

Separately, ports: "5432:5432" punches a hole from your host machine (your Mac) through to the container. The two numbers don't have to match — "5432:5433" would mean "reach the container's 5432 via my Mac's 5433 instead." We kept them equal everywhere for clarity.

The gotcha this caused for us

A network client doesn't just connect once — after the first connection, the server tells it the address to use for all future connections (the "advertised" address). If a container advertises its own service name, that address is meaningless to anything outside the Docker network — including every Spring Boot service we currently run directly on the host. Full story, and the actual bug this caused, in §9.

07 · this project

Volumes — where the data actually lives

A container's own filesystem is disposable — delete the container, lose everything written inside it. Volumes are how data survives that.

Named volume
vicinia-postgres-data:/var/lib/postgresql/data — Docker creates and manages this storage itself, outside any container's disposable filesystem. Postgres's actual data lives here, and survives the container being deleted and recreated.
Bind mount
./backend/docker/postgres-init:/docker-entrypoint-initdb.d — maps a real folder on your Mac straight into the container. We use this specifically so our committed SQL file is what seeds the databases, rather than baking that SQL into a custom image nobody else could easily edit.
Why editing the init script alone doesn't do anything

Postgres only runs files from /docker-entrypoint-initdb.d/ the very first time it starts against a truly empty data directory. Once vicinia-postgres-data has data in it, editing 001-create-databases.sql and re-running docker compose up changes nothing — the volume isn't empty anymore. The only way to force it to re-run init scripts is docker compose down -v (the -v deletes the named volumes too), which also means losing whatever was in the database.

08 · this project

Healthchecks — how start-infra.sh knows Postgres is really ready

"Container started" and "service ready to accept connections" are not the same moment — Postgres's process can be running for a second or two before it's actually accepting queries. A healthcheck block tells Docker how to ask "are you actually ready?", not just "are you running?":

healthcheck:
  test: ["CMD-SHELL", "pg_isready -U vicinia"]
  interval: 5s
  timeout: 5s
  retries: 10

Docker runs that command inside the container every 5 seconds and tracks a status: starting → healthy or unhealthy. Our three data services each have one (pg_isready for Postgres, redis-cli ping for Redis, rpk cluster health for Redpanda).

start-infra.sh polls this exact status before doing anything else:

# from start-infra.sh
status=$(docker inspect --format='{{.State.Health.Status}}' "$container")
# loops until status == "healthy" before starting any Spring Boot service

This is why the script waits for Postgres/Redis/Redpanda to report healthy before building or starting a single Java service — starting auth-service against a Postgres that's merely "running" but not yet "accepting connections" would just fail on its first database call.

09 · advanced

A real bug, explained: bind address vs. advertised address

The single most instructive Docker networking bug we hit building Vicinia — worth understanding on sight, because it isn't specific to Redpanda; it shows up in real Kafka, Redis Cluster, and most clustered systems.

9.1What happened

Redpanda was configured to advertise redpanda:9092 — its own service name, meaningful only inside the Docker network. Every Spring Boot service was, at that point, still running directly on the host (not in a container), connecting to Redpanda via localhost:9092. The very first connection succeeded — localhost:9092 is exactly what was configured. But the first thing a Kafka client does after connecting is ask for cluster metadata, and the broker's answer included its own advertised address for all future traffic: redpanda. A hostname that means nothing outside the Docker network. Every reconnect after that first one failed with UnknownHostException: redpanda.

9.2The fix, and why it's temporary

# docker-compose.infra.yml — redpanda service
--kafka-addr=PLAINTEXT://0.0.0.0:9092          # bind: listen on every interface
--advertise-kafka-addr=PLAINTEXT://localhost:9092  # advertise: what clients reconnect to

Advertising localhost:9092 is correct right now, because every client is a host-run process. It stops being correct the moment app services themselves move into containers on this same Docker network (Stage 19, see §10) — at that point it needs to flip back to redpanda:9092, because localhost inside a container refers to that container itself, not the Redpanda container next to it.

9.3Why restarting the container alone didn't fix already-running services

The already-running auth-service and user-service processes had already cached the bad metadata (redpanda:9092) from before the fix. A client stuck failing to connect to a bad address never gets the chance to fetch corrected metadata — it just keeps retrying the address it already has. Fixing the server side doesn't retroactively fix a client that's already wedged on a stale value; the JVMs had to be restarted to force a completely fresh bootstrap.

The generalizable lesson

Any time a network client behaves correctly on its first connection but fails on reconnect, suspect a bind-vs-advertise mismatch before anything else — the address you dial and the address the server hands back for next time are two different settings, and only one of them has to be wrong to cause exactly this symptom.

10 · advanced

Where Docker goes next for Vicinia

Everything above is Stage 0-2's reality: Docker running the data layer only, app services on the host. docs/BUILD_TRACKER.md Stage 19 is where that changes:

  • One Dockerfile per service — a multi-stage build: an early stage with the full JDK + Maven compiles the jar, a final stage copies just the jar onto a slim JRE-only base image, keeping the shipped image small (the build tools themselves never make it into the final image).
  • docker-compose.prod.yml — covering all 19 services plus Redpanda/Postgres/Redis, replacing today's host-run mvn spring-boot:run processes entirely.
  • GitHub Actions builds each changed service's image on merge to main and pushes it to GitHub Container Registry (GHCR).
  • The Oracle VM pulls updated images and restarts with docker compose pull && docker compose up -d — no manual deploy steps.

Full reasoning for the deployment target itself (why Oracle's free VM, why Redpanda over Kafka there too, the RAM budget) is in docs/DEPLOYMENT.md.

12 · reference

What never gets committed, and why

Every time you run ./start-infra.sh or open this project in an IDE, files appear that git status never mentions. That's .gitignore doing its job — here's exactly what it's hiding and why each entry earns its place.

EntryWhat it actually is
target/Maven's build output per module — compiled .class files and the packaged jar. Regenerated from source by mvn clean install every time; committing binary build output would bloat the repo's history with files that go stale the moment source changes, and differ machine to machine anyway.
*.log, logs/Runtime output from start-infra.sh's services. Different every run, purely diagnostic, no reason it should ever live in version control.
.pids/start-infra.sh's process-ID tracking files. Literally just numbers meaningful only to your machine's current run — wrong the moment you restart anything, meaningless on anyone else's machine.
.idea/, *.imlJetBrains IDE project metadata — window layout, run configurations, indexing cache. Personal editor state, not project source; committing it would force your exact IDE setup on every collaborator and generate merge conflicts over trivial things like which file tab was open.
.DS_StoremacOS Finder's per-folder metadata (icon positions, view settings). A pure Finder artifact — meaningless noise on Linux/Windows and in git history.
node_modules/, dist/, build/Frontend equivalents of target/: installed npm packages (huge, regenerable from package.json) and compiled frontend output.
.env, .env.localLocal environment overrides — the one category that must never be committed even by accident, since these commonly hold real secrets/credentials once the project has any.

12.1How the pattern syntax actually works

Our actual file:

# Java / Maven
target/
*.class
*.jar
!.mvn/wrapper/maven-wrapper.jar

# IDE
.idea/
*.iml
.vscode/
.DS_Store

# Node / React
node_modules/
dist/
build/
.env
.env.local

# Logs
*.log
logs/

# start-infra.sh / stop-infra.sh PID tracking
.pids/

# Docker
docker-compose.override.yml
  • A trailing slash (target/) matches a directory by that name, anywhere in the repo.
  • A leading * (*.jar) is a wildcard — matches any file with that extension, anywhere.
  • A leading ! is a negation — an exception carved out of a broader rule above it. !.mvn/wrapper/maven-wrapper.jar means: "ignore all jars in general (*.jar, since a working tree can accumulate build artifacts named *.jar), except this one specific jar — the Maven wrapper binary, which genuinely needs to be committed so anyone can run ./mvnw without installing Maven first."
The one gotcha worth knowing

.gitignore only stops new, untracked files from being picked up by git add. If a file was already committed before a rule was added to ignore it, adding the rule alone does nothing — git keeps tracking it. Fixing that needs git rm --cached <file> (removes it from tracking, leaves the actual file on disk untouched), then a commit. To check why a specific file is or isn't being ignored, git check-ignore -v <path> tells you exactly which rule, in which file, matched it.
