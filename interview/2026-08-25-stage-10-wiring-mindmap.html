Why it works

All 5 existing Kafka consumers — user-service, inventory-service, cart-service, order-service, payment-service — were checked one by one and confirmed already idempotent by construction: each checks whether its target state already reflects the event (does the profile exist, is the order still PAYMENT_PENDING) before mutating anything. None needed new idempotency logic. This stage's real work was the layer around them.

ARCHITECTURE.md is explicit: "Spring Kafka non-blocking retry topics, not blocking Thread.sleep." Inventory-service's product-events consumer had its own custom DefaultErrorHandler bean since Stage 5, built for a real, already-proven need (a cold-start REST call racing the load-balancer cache). That bean is gone now — replaced by @RetryableTopic with the same effective ~15–18s backoff window, via the mechanism the architecture actually specifies.

cart-service and user-service only ever consumed events — neither had ever needed a Kafka producer, so neither had a spring.kafka.producer block. @RetryableTopic's internal republishing to retry/DLT topics needs one. Spring Boot's autoconfigured default (a plain StringSerializer) tried to serialize a deserialized Java object and threw ClassCastException — invisible until a deliberate failure actually exercised the republish path.

Spring Kafka names retry/DLT topics after the source topic by default, not the consumer group. cart-service and payment-service both apply @RetryableTopic to order-events; user-service and payment-service both apply it to user-events. Publishing one malformed event caused both services' @DltHandlers to fire on it — confirmed directly in the logs, not inferred. Fixed with explicit, service-qualified suffixes on all 5 listeners, including the 2 with no collision today, since the same bug would recur silently the moment any topic gains a second consumer.

  • A hand-crafted order.confirmed event, published directly to the topic, with a payload userId that isn't a valid UUID — a deterministic, reproducible failure needing no external dependency to trigger reliably.
  • First run (before the naming fix): both cart-service's and payment-service's DLQ handlers fired — proof of bug two.
  • Second run (after the fix): only cart-service's fired, payment-service's DLT stayed empty — proof of the fix, not just the absence of an error.
  • Retry-topic message counts confirmed genuine retries happened (not an instant skip) before the message landed in the DLQ.
  • A full happy-path checkout — wallet topup, order, CONFIRMED, cart cleared — re-verified clean afterward.
Both bugs sound like they'd be obvious from reading the code — why weren't they caught until an actual failure was triggered?
Because both only exist in a code path that only runs when something has already gone wrong — the happy path, which is what every prior test in this project exercised, never touches the republish-to-retry-topic machinery at all. A consumer that only ever succeeds never asks its producer to serialize anything, so a missing producer config is invisible; two consumer groups on the same topic never reveal a naming collision until one of them actually dead-letters a message the other is also subscribed to receive. This is exactly why the checklist item says "deliberately trigger one failure" rather than "add retry annotations" — the annotations alone prove nothing about whether the failure path actually works, only running it does.
Only two pairs of consumer groups actually collided today — why add the explicit suffix to inventory-service's and order-service's listeners too, when nothing is wrong with them right now?
Because "nothing is wrong right now" and "nothing will ever be wrong" are different claims, and only the second one would justify leaving the default naming in place. product-events has exactly one consumer today, but notification-service (Stage 12) is explicitly planned to consume several of these same topics later — at that point, the identical collision would reappear, silently, with no code change anywhere near the two services actually affected making it hard to trace back to "two annotations both used the default name." Naming the suffix explicitly costs one line per listener and closes the entire bug class for good, rather than leaving a trap for whichever future stage happens to add the second consumer.
Once the fix was in place and the test passed, wasn't that enough — why does the write-up emphasize running it a second time?
Because a single passing run after a fix proves the fix didn't break anything new, but it doesn't by itself prove the fix actually addressed the original bug — the same "only cart-service's DLT got the message" result could, in principle, occur for an unrelated reason if the first run's failure mode had never been precisely understood. Running the identical test once *before* the fix (both handlers fire — the bug reproduces on demand) and once *after* (only the correct one fires) turns "the fix seems to work" into "the fix changed exactly the behavior it was meant to change, confirmed by the same test both times." That before/after pairing is what makes a bug fix a proven fix rather than a plausible one.
