Why it works

JwtTokenProvider signs HS256 access tokens (15-min TTL) carrying jti/sub/email/roles/permissions, using a key built via Keys.hmacShaKeyFor(secret) — the same secret is pulled from config-server by both auth-service (issues) and api-gateway (verifies).

InternalRequestFilter is a plain jakarta.servlet.Filter — deliberately not a Spring @Component. EventEnvelope<T> wraps every Kafka payload with eventId/eventType/schemaVersion/occurredAt per ARCHITECTURE.md §9.

why no Spring annotations in commonAnnotating classes in a shared module with @Component only works if every consumer's component-scan reaches that package — easy to get wrong across module boundaries. Each service instead wires these as explicit @Bean methods reading its own @Value config. It also keeps jakarta.servlet-api a provided-scope dependency of common, so api-gateway (WebFlux, no servlet API at all) can depend on the module for JwtTokenProvider without ever touching the servlet-based filter class.

Two many-to-many joins: Role↔Permission and UserCredential↔Role. RoleSeeder (a CommandLineRunner) creates the 4 V1 roles and their permission bundles on first boot if the table is empty. UserCredential's primary key is a Hibernate-native GenerationType.UUID — that exact UUID becomes the JWT sub claim and, later, user-service's UserProfile.id.

why model permissions now for 4 rolesA role is a name plus a set of permissions, not a bare string. Adding SUPPORT_AGENT or MERCHANT_STAFF later is then a new seeded row with a scoped permission bundle — a config change, not a schema migration (ADR 0006).
  • signup — email-uniqueness check, blocks self-registering as ADMIN, bcrypt-hashes the password, saves, publishes user.registered, then issues tokens exactly like login.
  • refresh — the opaque token is validated and deleted in one step (rotation): a stolen refresh token only works once. The client sends userId alongside it, matching the documented Redis key refresh:{userId} exactly, so there's no separate token→user reverse index to keep in sync.
  • logout — reads the raw Authorization header directly (not the gateway's X-User-Id) and parses it itself to get jti + exact expiry, so the blacklist TTL is bounded to the token's own remaining life, never longer. Idempotent: a garbage or already-expired token is silently a no-op.
  • forgot/reset-password — a 15-minute, one-time Redis token. The forgot-password response is identical whether or not the email exists (no account enumeration); reset revokes every existing refresh session, forcing re-login everywhere.

There is no POST /users endpoint. UserEventConsumer reacts to user.registered and creates the UserProfile row — idempotent via a plain existsById check before insert, which is itself the natural state-check for this case (no separate processed_events table needed).

The consumer deserializes into its own local UserEventEnvelope record, not auth-service's Java classes.

why a local envelope, not a shared typeJackson's default JSON type headers embed the producer's fully-qualified class name (e.g. com.vicinia.authservice.messaging.UserRegisteredPayload) — which doesn't exist on user-service's classpath, since they're separate deployable modules. Producer-side spring.json.add.type.headers=false plus a consumer-side default type avoids that entirely; the envelope's payload is read as a plain Map and picked apart by hand for whichever eventType is recognized.

One GlobalFilter at Ordered.HIGHEST_PRECEDENCE runs on every proxied request. First it always strips any client-supplied X-User-*/X-Internal-Secret headers and re-stamps the real internal secret. If the path matches vicinia.gateway.public-paths (via AntPathMatcher), it forwards immediately. Otherwise it requires a Bearer token, parses it with the shared JwtTokenProvider, checks blacklist:{jti} reactively via ReactiveStringRedisTemplate, and only then injects X-User-Id/Email/Roles/Permissions from the verified claims.

why strip headers before checking anythingIf the strip happened only on the protected-path branch, a request to a public path could still smuggle a forged X-User-Id straight through to a service that trusts it blindly. Stripping unconditionally, before the public/protected branch, closes that gap.
  • Port collision. Redpanda's pandaproxy/schema-registry were mapped to host ports 8081/8082 in Stage 1 — invisible until Stage 2 actually tried to bind auth-service/user-service to those same ports. Fixed by remapping the host side only, to 18081/18082.
  • Unreachable advertised address. Redpanda advertised redpanda:9092 — a hostname that only resolves inside the Docker network. Every service currently runs on the host via mvn spring-boot:run, so every reconnect after the first bootstrap failed with UnknownHostException. Fixed by advertising localhost:9092 for this stage; will flip back to the container hostname once app services are themselves containerized (Stage 19). Already-running services also needed a restart — they'd cached the bad broker metadata and kept retrying it even after the container was fixed.
  • Spring bean-name collision. A custom GatewayProperties class collided by default bean name with Spring Cloud Gateway's own internal gatewayProperties bean (same simple class name, different package). Renamed to PublicPathsProperties.
  • Signup → RBAC roles/permissions correctly on the token; profile 404 until the Kafka event lands, then 200.
  • Login: correct password 200, wrong password 401. Duplicate email 409. Self-registering as ADMIN 400.
  • Refresh rotates the token; reusing the old refresh token afterward is 401.
  • Logout blacklists the access token; reusing it afterward is 401.
  • Forgot/reset-password: reset works once, a second attempt with the same token is 401.
  • Hitting auth-service or user-service directly on their own ports, bypassing the gateway, is 403.
  • All Spring Boot processes killed and docker compose down — nothing left running.
Why is the access token a signed JWT but the refresh token a random UUID?
The access token needs to be verified without a database round-trip on every request — that's the entire point of a self-contained signed token; the gateway checks a signature, not a table. A refresh token, by contrast, is presented rarely and needs to be revocable — logout, password reset, or a detected compromise all need to kill it immediately. A signed JWT can't be un-signed; an opaque, server-stored token can simply be deleted. Building it as a JWT would just mean bolting a blacklist onto it anyway, at which point it isn't gaining anything over an opaque token.
What actually stops someone from swapping the roles/permissions claims in their own JWT?
The HMAC signature. Any change to the payload — even one character — invalidates the signature check against the shared secret, which only auth-service and api-gateway hold. This is also exactly why the secret has to be long enough for HS256 (32+ bytes) and never logged or committed anywhere real.
Isn't a role string ("CUSTOMER") simpler than a role+permission join table?
Simpler to write today, more expensive the first time a role needs to change shape. With permissions modeled explicitly, "give merchants read-only access to their own settlement history" is granting one existing permission to one role — no code change, no redeploy. With a bare role string, every permission check is an if (role.equals("MERCHANT")) scattered across services, and a new access pattern means touching all of them.
Why bake permissions into the JWT instead of looking them up per-request?
Same reasoning as access-vs-refresh above: a per-request DB lookup for authorization defeats the purpose of a stateless token. The tradeoff, made explicitly here, is that a permission change doesn't take effect for a given user until their current token expires (≤15 minutes) — acceptable for V1, and the exact kind of tradeoff worth being able to name out loud rather than not noticing it exists.
What's the actual risk if the consumer processed the same event twice?
A second attempt to insert a UserProfile with the same id would hit the primary key — but far worse, imagine this were an inventory or payment event: double-processing a "confirm payment" event could double-credit an account. Checking current state before applying (does this profile already exist?) is what makes the operation safe to run more than once, which matters because Kafka's at-least-once delivery guarantees a consumer restart can replay events it already saw.
Would a shared Java module with the event types have been simpler?
For two services, marginally. At 16 services all consuming a handful of aggregates' events, a shared schema module becomes a coordination bottleneck — every consumer's deploy is now coupled to that module's version. Treating the wire format as the contract (JSON shape, not a shared class) is what actually keeps 16 services independently deployable, which is the entire premise of the architecture.
Why one filter for all 13 routes instead of attaching auth to each route definition?
A per-route filter has to be remembered on every single route — miss it once on a new service's route and that service is silently wide open. A GlobalFilter runs on everything by construction; the routes stay declarative (just path → destination), and the security decision (public vs. protected) lives in exactly one place, the public-paths list, instead of being duplicated across 13 route definitions.
Why does it need Redis at all if the JWT signature is already enough to trust the token?
A valid signature only proves the token was legitimately issued — not that it's still supposed to be usable right now. Logout has to actually revoke access before natural expiry, and a signature check alone can never express "this specific token, no longer." That's the one thing the blacklist adds that the JWT alone structurally cannot.
Why is the blacklist TTL computed per-token instead of a fixed value?
blacklist:{jti} is set to expire at exactly the token's own remaining lifetime (Duration.between(now, expiresAt)), never longer. A fixed 15-minute TTL would usually be fine since that's the access-token lifetime anyway, but computing it exactly means the blacklist entry can never outlive the token it's blocking — no stale entries accumulating in Redis for tokens that would've expired naturally anyway.
Why does refresh-token rotation delete-then-reissue instead of just extending the same token?
If a refresh token were reusable indefinitely until its 30-day TTL, a leaked token would work for the attacker for up to 30 days with no signal to the real user. Rotation means a stolen-and-used token immediately fails for the legitimate user's next refresh — a detectable, actionable signal — rather than silently coexisting.
Why did the Kafka connection fail on reconnect rather than the very first attempt?
The first connection to localhost:9092 (the bootstrap server) always succeeds — that's just what's in the config. But the very first thing a Kafka client does after connecting is ask for cluster metadata, and the broker answers with its advertised address for all future traffic. Once that address is redpanda — meaningless outside the Docker network — every subsequent connection attempt targets a hostname the host machine can't resolve. The bootstrap address and the address actually used are different things, and only the second one was wrong.
Why didn't fixing the container immediately fix the running services?
The already-running auth-service and user-service had already cached the broker metadata pointing at the old, unreachable redpanda:9092, and a client stuck failing to connect never gets the chance to re-fetch corrected metadata — it just keeps retrying the stale address. Restarting the JVMs was necessary to force a completely fresh bootstrap. This is a good general lesson: fixing the server side of a cached-address problem doesn't retroactively fix clients that are already wedged on the bad value.
