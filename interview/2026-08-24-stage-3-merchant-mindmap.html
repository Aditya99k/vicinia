Why it works

Full 8-state machine (PENDING_REVIEW → APPROVED → ONBOARDING → LIVE, plus REJECTED/SUSPENDED/TEMP_CLOSED/PERMANENTLY_CLOSED) with one dedicated class, MerchantStatusTransition, as the single source of truth for what's legal — a static EnumMap<Status, Set<Status>> that every transition in the service goes through via merchant.transitionTo(target).

why centralize this instead of checking inline per-endpointSeven different endpoints (go-live, close, reopen, approve, reject, suspend, reinstate) each change status. Checking "is this move legal?" inline in each one means seven places that could each get the rule slightly wrong or drift out of sync. One shared guard means the rule is defined exactly once, and every endpoint fails identically when it's violated.
  • POST /api/merchants/apply — one merchant per ownerUserId (unique constraint), a list of document metadata (type + reference URL — no real file upload yet, that's a future Cloudinary integration), store address, defaults to a 5km delivery radius.
  • PUT /me/hours, PUT /me — business hours and store profile, editable by the owning merchant.
  • go-live is gated on hours being set — the full "at least one catalog listing" gate from the architecture doc can't be enforced yet since catalog-service doesn't exist until Stage 4. Documented as a deliberate, temporary simplification.

Approve, reject, suspend, reinstate, and the pending-review list all require the MERCHANT_APPROVE permission — the same one seeded onto ADMIN back in Stage 2's RoleSeeder. Checked via a plain X-User-Permissions header read (PermissionUtil.require(...)), not a Spring Security framework — matches the hand-rolled style already used for JWT and internal-secret checks elsewhere.

Published to merchant-events, partitioned by merchantId, via common's EventEnvelope — same pattern as auth-service's user.registered in Stage 2. No consumers exist yet (catalog-service, notification-service) — expected at this point in the build, not a gap.

Installs dependencies on first run, starts customer-app, waits for it to actually respond, and prints both the localhost and LAN URLs (LAN IP detected live via ipconfig) in the summary. Fixing stop-infra.sh to actually tear it back down surfaced two real bugs in a row.

bug 1 — the process sanity-check never matched itstop-infra.sh's "does this PID still look like our process" regex only checked for spring-boot:run|java. The frontend process didn't match either, so it was silently skipped — left running every time, with no error.

Fixed the regex, then found bug 2: even matching, killing the tracked PID (npm run dev -- --host) left a second, orphaned process still holding port 5173 — npm doesn't reliably forward SIGTERM to the vite/node child it spawns. Fixed by launching ./node_modules/.bin/vite --host directly, so the tracked PID is the real server, no wrapper process in between. See Deep Dives for the general version of this lesson.

  • Apply → 201 PENDING_REVIEW; duplicate apply → 409.
  • Go-live pre-approval → blocked twice over: the hours gate, and independently, the raw transition guard (PENDING_REVIEW → LIVE isn't in the allowed set at all).
  • Admin approve → the double PENDING_REVIEW → APPROVED → ONBOARDING transition in one call, with merchant.approved actually consumed off Redpanda to confirm key and payload — not just assumed sent.
  • Non-admin hitting an admin endpoint → 403 with the specific missing permission named.
  • Go-live once approved+hours-set → LIVE, shows up in public /nearby; suspend → gone from /nearby, merchant.suspended confirmed on Kafka, double-suspend → 409; reinstate → LIVE again; reject → REJECTED, then reject-into-approve → 409 confirming it's terminal.
  • start-infra.sh / stop-infra.sh: fresh start, re-run idempotency (frontend correctly no-ops on a second start), and a clean stop verified with nothing orphaned — processes, containers, or PID files.
The architecture doc says approve fires an event, then transitions to ONBOARDING — why not model that as two separate admin-triggered steps?
Because nothing else needs to happen in between. The event is what other services (eventually) react to; the ONBOARDING transition is a bookkeeping detail entirely internal to merchant-service itself. Splitting it into two admin-callable steps would just mean admins have to remember to always call the second one, for a distinction that carries no information to anyone outside the service. Publish the event where the state semantically becomes APPROVED, then move on immediately — one admin action, one API call, two recorded transitions.
Isn't checking a raw header string for a permission name fragile compared to a real authorization framework?
It would be, if this service were the thing establishing trust. It isn't — api-gateway already did the actual authentication (verified the JWT, checked the blacklist) before this header ever arrives, and InternalRequestFilter already guarantees the request came through the gateway and not directly. By the time PermissionUtil.require(...) runs, the only open question left is "does this already-authenticated, already-gateway-verified caller have this one specific permission" — a single string-membership check, which is genuinely all that's left to decide. Pulling in a full authorization framework here would be solving a problem that api-gateway already solved.
Why did tracking npm's PID leave an orphaned process at all — isn't a child process killed when its parent dies?
Not automatically, and not reliably through npm specifically. A process only dies when it receives and acts on a signal (or its parent's death happens to trigger something like a SIGHUP it doesn't ignore) — npm as a wrapper has a known history of not forwarding SIGTERM/SIGINT to the child it spawns for a script, so the child can simply keep running, now parentless, still holding whatever port or resource it had. This is the same general class of bug as the earlier auth-token-caching issue this project hit: something upstream changed or died, but a downstream thing that already has what it needs just keeps going, oblivious.
What's the general rule for avoiding this class of bug?
When a script backgrounds a process specifically so it can be tracked and killed later, track the actual long-running process, not a wrapper/launcher around it — invoke the real binary directly wherever possible (here: node_modules/.bin/vite instead of npm run dev). If a wrapper is unavoidable, verify empirically that killing the tracked PID actually kills the whole subtree, don't assume it — which is exactly how this bug was caught: comparing lsof -ti:5173 against the PID file directly, instead of trusting the stop script's own "success" output.
Merchant already stores latitude/longitude/deliveryRadiusKm — why doesn't /nearby actually filter by distance yet?
Because that's a deliberate, already-decided service boundary, not a missing feature: ARCHITECTURE.md §7 puts geo-radius search in inventory-service (Redis GEORADIUS queries against merchant listings), not merchant-service, since "which stores are near me" and "which of those stores have this product in stock nearby" are really one combined query once inventory-service exists. Building distance math here now would mean building it twice, or building the wrong half of it — merchant-service's job is just merchant identity and status, filtering to LIVE is the correct scope for it alone.
