Why it works

No Postgres, no Mongo — Redis is the entire storage layer (ARCHITECTURE.md §12), 7-day rolling TTL, reset on every write. The whole cart (userId, merchantId, line items) round-trips as one value under a single key. Cart is a plain mutable class with named mutation methods — addOrIncrement, removeItem — not a DTO with public setters, so the Redis serializer is configured to read/write its fields directly rather than forcing bean-style accessors onto a domain object that doesn't need them.

Adding an item pins the cart to that listing's merchant the first time; adding a different merchant's item afterward is rejected outright — 409, cart left untouched — rather than silently replacing what was there. The client has to explicitly clear the cart first. Removing the last item resets the pin to null, confirmed by then successfully adding a different merchant's item to the now-empty cart.

The cart itself only ever stores a listingId and a quantity — never a price. Every read re-fetches each line's current price/stock/name from inventory-service and computes available fresh. Adding more than what's currently in stock is allowed (write-time only checks the listing exists and is active) — an over-quantity line is flagged available:false with lineTotal:null at read time and excluded from the subtotal, rather than being blocked outright.

why not block the writeStock is dynamic and reservations don't exist until checkout (Stage 8). Enforcing sufficiency at write time would just be a second, redundant, and quickly-stale copy of a check the read path already does correctly and live — one source of truth, checked at the moment it actually matters.

ListingController only had create/mine/update/by-productId — nothing to fetch one specific listing by its own id, which cart-service's enrichment needs on every read. Added GET /api/inventory/listings/{id}, deliberately not added to api-gateway's public-paths since it's only ever meant to be called service-to-service — verified both directions: 401 through the gateway with no JWT, 200 hit directly with just the internal secret, exactly matching how cart-service's own InventoryClient calls it.

ARCHITECTURE.md §7 lists two dependencies for cart-service beyond catalog/inventory: consuming order.confirmed to auto-clear the cart, and validating coupons against coupon-service. Neither is in this stage's actual BUILD_TRACKER checklist, and neither has a real counterpart to build against yet — order-service is Stage 8, coupon-service is Stage 7. Building either now would mean a consumer or client with nothing genuine to test.

  • Unauthenticated → 401; direct hit on cart-service's own port, bypassing the gateway → 403.
  • Empty cart for a fresh user; add → merchant pin + correct price/subtotal; persistence confirmed via a separate GET.
  • Different-merchant add → 409, cart unchanged; unknown listingId → 404; updating a listingId not in the cart → 404.
  • Over-quantity update → succeeds, flagged unavailable, excluded from subtotal; setting it back → available again.
  • Remove last item → merchant pin resets to null; clear → Redis key actually gone (checked directly); clearing again → still 204, idempotent.
  • TTL on the key confirmed ~7 days directly against Redis; two different users' carts confirmed fully independent.
Wouldn't it be simpler and faster to snapshot the price when an item is added, instead of calling inventory-service on every single read?
Simpler to write, but wrong the moment a merchant changes a price or runs out of stock while an item sits in someone's cart — which, given a 7-day TTL, is the common case, not the edge case. A snapshotted price is a claim about the past being presented as the present; a customer could reach checkout expecting a price that hasn't been true for days. The whole reason this stage's checklist calls out a "live" check specifically is that a cart's job isn't to remember what something cost when it was added — it's to always answer "what would I pay right now," which only the system that actually owns price and stock can answer truthfully.
ADR 0001 says a different-merchant add can either replace the cart or prompt the user — why pick the more restrictive option instead of just clearing and adding automatically?
Because "prompt the user" is a frontend decision cart-service can't make on its own — a REST API has no way to show a confirmation dialog. The only two implementable options are silently discard the customer's existing cart, or refuse and say why. Silently discarding someone's cart contents because of an action they took to add something else, with no confirmation, is exactly the kind of surprising data loss this project's own working style tries to avoid elsewhere (see: never running a destructive operation without being explicit about it). A 409 with a clear message is the one option a frontend can always turn into that prompt later — the reverse isn't true.
Every DTO in this project so far is a Java record — why does Cart go back to a mutable class with a protected no-arg constructor?
Records are the right shape for the DTOs — immutable data being handed across a boundary once, built fresh each time. Cart is different: it's loaded from Redis, mutated in place through several possible operations (increment an existing line vs. add a new one, drop the merchant pin only when the last item goes), and saved back — genuinely closer to how Merchant or Product behave elsewhere in this project (mutator methods like transitionTo, not reconstruction) than to a request/response shape. The cost is that Jackson needs an explicit field-visibility configuration to serialize a class with no public setters — a one-time, contained cost in RedisConfig, in exchange for not scattering "always rebuild the whole object to change one quantity" logic across the service layer.
Stage 5 introduced atomic updates, a scheduled reaper, and the first Kafka consumer — Stage 6 feels comparatively simple. Is that a sign something was skipped?
No — it's a sign the hard problem for this stage was already solved somewhere else. Stage 5 had to invent real machinery because oversell correctness is a genuinely hard problem with no shortcut. Cart-service's actual job — remember a few line items per user, cheaply, for a limited time — is not a hard problem, and ADR 0001 already made the one interesting design decision (single merchant) before this stage even started. Building elaborate machinery here anyway, when Redis's built-in TTL and a service-to-service REST call already fully solve what's being asked, would be solving a problem that doesn't exist instead of the one that does. Matching implementation complexity to the actual difficulty of the problem — not to how much code a service "should" have — is itself the discipline.
