Why it works

docker-compose.infra.yml had Postgres's user/password as plaintext literals. config-server/config-repo/application.yml had the internal-request secret and the JWT signing key as plaintext literals — both already pushed to GitHub across earlier Stage 2 commits.

why this matters even on a private repoA secret committed to git history is compromised the moment it's committed, regardless of who can currently see the repo — access can change, the repo can be forked, forgotten collaborators can still have old clones. The fix is never "delete it from the current file," it's "treat it as burned and rotate."
  • .env (gitignored) holds real values; .env.example (committed) holds the same keys with instructions and the exact command to generate each one.
  • docker-compose.infra.yml: POSTGRES_USER: vicinia → POSTGRES_USER: ${POSTGRES_USER} — Compose loads .env automatically since it sits next to the file.
  • config-repo/application.yml: both secrets replaced with ${VICINIA_INTERNAL_SECRET} / ${VICINIA_JWT_SECRET}.
  • auth-service/user-service application.yml: datasource username/password switched to the same ${POSTGRES_USER}/${POSTGRES_PASSWORD} — one source of truth instead of the value duplicated three places.

A new first step: refuse to start at all if .env is missing (pointing at .env.example), otherwise source it with set -a/set +a (auto-exports every variable it defines), then check a REQUIRED_ENV_VARS list and fail loud — naming exactly which key is missing — rather than let a service fail 30 seconds later with an opaque Spring placeholder-resolution stack trace.

why set -a instead of manually exporting each varset -a marks every variable assignment for auto-export while it's on, so a plain source .env exports all five keys in one line instead of five separate export statements to keep in sync with the file.
  • Generated fresh VICINIA_INTERNAL_SECRET and VICINIA_JWT_SECRET values — the old, already-leaked ones are retired, not reused.
  • Full stack up via the updated start-infra.sh: real signup through the gateway, a real JWT issued.
  • Gateway-validated protected request (GET /api/users/me/profile) → 200 — proves auth-service and api-gateway independently resolved the same JWT secret from two different processes.
  • Direct hit on user-service's own port, bypassing the gateway → 403 — proves the internal secret resolved correctly too.
  • Confirmed git status never shows .env, and git check-ignore -v .env names the exact rule matching it, before staging anything.
Does Config Server itself need VICINIA_JWT_SECRET set in its environment?
No — and that's the interesting part. Config Server's native backend just reads the YAML file into a property map and serves it as JSON/text; it never instantiates a bean that would trigger placeholder resolution on that value. It hands the literal string "${VICINIA_JWT_SECRET}" to whoever asks, unresolved.
So who actually resolves it, and when?
The consuming service — auth-service or api-gateway. When something does @Value("${vicinia.jwt.secret}"), Spring resolves that placeholder against the service's own merged Environment, gets back the string "${VICINIA_JWT_SECRET}", and — because Spring's placeholder resolution is recursive by design — immediately resolves that nested placeholder too, this time against the same service's own OS environment variables. Two completely separate JVM processes, each resolving independently against their own environment, landing on the identical value only because start-infra.sh exported the same .env into both. Confirmed empirically today, not just reasoned about: both auth-service (issuer) and api-gateway (verifier) had to agree for the login flow to work at all, and it did.
Removing the secret from the current file doesn't remove it from history — why not just rewrite history and be done with it?
Tools like git filter-repo or BFG can scrub a value from every commit, but it rewrites every commit hash after the point of change, which means a forced push and every existing clone becoming incompatible with the rewritten history. That's a genuinely disruptive, higher-blast-radius operation — appropriate for a public repo or one with other collaborators, much less clearly worth it for a private, single-developer, pre-production repo where the actual fix (a leaked value no longer being valid) is achieved just as completely by rotation alone.
What does rotation alone actually guarantee, and what does it not?
It guarantees the old value can never be used to forge a token or bypass the gateway again — it's just an inert string in old commits now. It does not hide the fact that a secret briefly lived in git history, which is why this is framed as a documented tradeoff rather than a fully solved problem — the honest version of "fixed," not the theatrical one.
What does set -a actually toggle?
It's short for set -o allexport — while it's on, every variable assignment (not just ones with an explicit export keyword) is automatically marked for export into the environment of any child process the shell launches. set +a turns that behavior back off immediately after, so it doesn't silently affect unrelated variables set later in the script.
Why does this matter for a plain KEY=value .env file specifically?
.env files are written as ordinary shell assignments (POSTGRES_USER=vicinia, no export keyword) precisely so they're readable by non-shell tools too (like Docker Compose's own native .env loader). Sourcing that file in bash without set -a would set those as local shell variables only — visible to the script itself, but invisible to any child process it launches, including every mvn spring-boot:run the script starts. set -a is what makes one file work for both.
