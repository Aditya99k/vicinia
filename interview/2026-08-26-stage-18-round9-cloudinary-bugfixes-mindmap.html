Why it works

Product photos previously came from nowhere real — placeholder art keyed off category. catalog-service now exposes GET /api/catalog/uploads/sign, which mints a short-lived HMAC-SHA1 signature over the sorted upload params plus the account's api secret (Cloudinary's own documented algorithm). The browser uploads the actual image bytes straight to api.cloudinary.com — never through our backend — using that signature. The merchant's "request a new product" form now has a real photo picker wired to it, and the uploaded secure_url flows into the same images field the admin-approval pipeline already understood.

Verified for real, not just compiled: signed a live request with the user's actual Cloudinary credentials, uploaded a genuine test PNG straight to api.cloudinary.com/v1_1/yhmq6jbb/image/upload with that signature, and got back a real secure_url — the full path, not a mock of it.

Address capture now offers "Use my current location" ( navigator.geolocation, same pattern already used for merchant store setup and rider go-online). That lat/lng rides along with the address, and at checkout it's snapshotted directly onto the order — a deliberate copy, not a live join back to the address table, matching how cart line items already snapshot price and name at add-time rather than re-reading the product live. The delivery partner's active-task card now renders a "Navigate to drop-off" link straight into Google Maps directions whenever that snapshot exists.

Two new legal transitions — READY_FOR_PICKUP → CANCELLED and DELIVERY_ASSIGNED → CANCELLED — give a merchant an escape hatch when no rider ever collects a ready order. POST /api/orders/{id}/merchant-cancel releases the inventory reservation and publishes order.cancelled, which merchant-service's existing consumer now also handles (branching on eventType inside the one listener it already had, rather than adding a second listener on the same topic and groupId — that split would have handed each event to only one of the two consumers, non-deterministically). The queue itself now also surfaces order-service's own live status while a task sits at READY — "awaiting pickup" vs. "rider assigned" vs. "picked up, out for delivery" — instead of one static label the whole time.

  • New DELETE /api/notifications/mine, wired to a "Clear all" button in the bell dropdown for every role.
  • Cart and order item rows now link through to the same product detail page search already reaches, instead of being inert rows.
  • The merchant settlement "Entries" tab fetches each order's full detail and renders real item photos/names alongside gross/commission/net, instead of a bare total per row.

The static "Hi <name>" banner is now three auto-scrolling slides (greeting, quick-delivery pitch, shop-local pitch), each with its own illustration, pausing on hover. First attempt used a flex track three times the container's width, translated left with transform — visually correct in isolation, but it broke the page layout around it (see Deep Dive 02). Rebuilt as cross-fading, absolutely-positioned slides that are never wider than the carousel itself.

The merchant cancel endpoint returned success, order-service showed CANCELLED — so why did the order stay stuck in the merchant's queue?
The frontend was innocent. Querying merchant_db directly showed the task still sitting at READY, and the merchant-service log had the real answer: ERROR ... constraint [merchant_order_tasks_status_check], thrown from exactly the new cancelFromOrderEvent method, retried four times, then dead-lettered. Hibernate had generated that CHECK constraint — status IN ('PENDING_ACCEPTANCE','ACCEPTED','REJECTED','READY','COMPLETED') — back when the table was first created, before CANCELLED existed as a value. ddl-auto: update only ever adds tables and columns it doesn't recognize; it never goes back and rewrites a constraint that's already there, even after the Java enum grows a new case. The Kafka event was arriving correctly, being consumed correctly, and failing at the very last step — a database refusing a value the application layer considered perfectly legal.
Was this a code bug, then?
No — and that distinction mattered for the fix. This dev database's table predates the enum change; a brand-new environment (CI's Testcontainers, a fresh clone) creates the table from the current enum and never hits this. The fix was operational: drop and recreate the constraint with CANCELLED included, then hand-correct the two orders that had already gotten stuck mid-cancel while the bug was live. No Java changed. The lesson that does carry forward: a passing ddl-auto: update startup is not proof a schema is current — it only proves nothing NEW was needed, which is a different claim than nothing changed.
The carousel's own wrapper had overflow: hidden — so how did a 300%-wide inner track manage to blow out a grid column two levels up?
overflow: hidden only controls what's painted, not what's measured. .home-grid was grid-template-columns: 1fr 320px — a bare 1fr, whose automatic minimum width defaults to its content's min-content size unless told otherwise. The flex track inside the carousel, laid out as three full-width cards side by side with flex-wrap: nowrap, has a min-content width of roughly three card-widths — and that measurement propagates up through the layout tree regardless of a nested element clipping the paint. The grid column grew to accommodate it, and the 320px sidebar got pushed clean off the viewport. Visually this read as "everything zoomed in," because the whole first column — hero card included — was now rendering at roughly 3x its intended width.
Why switch to absolute positioning instead of just fixing the width somewhere?
Because the real fix has two independent halves, and skipping either one leaves the bug latent. minmax(0, 1fr) on the grid column caps the automatic minimum at zero — that alone stops today's blowout. But leaving the carousel's own mechanism as a 300%-wide translated track means the next person to add a fourth slide, or nest it one level deeper, can reintroduce the exact same class of bug. Cross-fading, absolutely-positioned slides have no element anywhere in the carousel that is ever wider than the carousel's own box — the failure mode isn't patched, it's structurally unavailable. Both changes shipped together on purpose.
OrderStatusTransitionTest failed right after the merchant-cancel push — wasn't that the same test suite that already covered CANCELLED transitions?
It covered the two CANCELLED transitions that existed when Stage 17 wrote it — from CREATED, from CONFIRMED, from PREPARING. That test's whole design (see Day 5's own deep dive on it) is a hand-maintained map of every legal (from, to) pair, asserted exhaustively against every possible pair the real enum can produce — which means the map is a second, independent copy of "what's legal" that has to be kept in sync with OrderStatusTransition.java by hand. Adding READY_FOR_PICKUP → CANCELLED and DELIVERY_ASSIGNED → CANCELLED to the production transition table without updating the test's own copy left the test asserting those two jumps should still throw — and CI caught exactly that gap, on the very next push.
So this wasn't a flaky test or a CI infrastructure problem?
No — gh run view --log-failed showed a clean AssertionError from the parameterized case, not a timeout or a Testcontainers flake. That's the useful signal an exhaustive-matrix test is built to give: a real behavior change that wasn't mirrored into the test's own oracle. The fix was one line per new transition, verified locally first (mvn test -Dtest=OrderStatusTransitionTest, clean target dirs, not a stale incremental build) before pushing — same discipline as every other CI fix this project has needed.
Why does catalog-service only ever hand out a signature, instead of accepting the file upload itself and forwarding it to Cloudinary?
Proxying the upload would mean every product photo's bytes pass through our own Spring app twice — once in from the merchant's browser, once back out to Cloudinary — burning our own bandwidth and memory for a job a CDN already exists to do directly. The signed-upload pattern instead treats the backend purely as an authority: it knows the api secret and can vouch, for the next 300-ish seconds, that a specific set of upload parameters (folder, timestamp) is authorized — and Cloudinary, holding the same secret, can independently recompute that HMAC and agree. Nothing about the actual image ever needs to be trusted or inspected server-side to make that guarantee hold.
Doesn't putting the api key in the browser leak it?
The api key is meant to be public — Cloudinary's own docs treat it like a client id, not a secret. The api secret never leaves catalog-service; it's only ever used server-side to compute the signature, and .env (holding it, alongside the key and cloud name) stays git-ignored, same as every other credential in this project. What ships to the browser is the signature itself — a one-time-use token scoped to one specific upload request, not the key that could mint arbitrary future ones.
