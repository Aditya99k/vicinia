Why it works

Placing an order with paymentMethod: RAZORPAY makes a genuine HTTP call to api.razorpay.com/v1/orders, HTTP Basic auth with the test-mode key id/secret the user provided (test mode — cannot move real money), and gets back a real order id from Razorpay's own servers. No mocking, no stub — the actual documented contract, exercised for real.

Wallet's pay call answers synchronously, in the same HTTP response. Razorpay can't — the customer completes payment on Razorpay's own hosted UI, whenever that happens. The order stays PAYMENT_PENDING after the initial call, returning razorpayOrderId/razorpayKeyId — everything a frontend needs for Checkout.js once one exists (Stage 18) — and resolves only when order-service's new Kafka consumer reacts to a webhook-driven payment.success/payment.failed.

No public HTTPS endpoint exists locally to register a real webhook with Razorpay's dashboard — so RAZORPAY_WEBHOOK_SECRET is generated locally, documented as a stand-in. That didn't limit verification: constructing a payment.captured payload and computing HMAC-SHA256(rawBody, secret) by hand is the exact same computation Razorpay's servers do, so both directions are genuinely proven — a correctly-signed payload resolves the order to CONFIRMED (inventory confirm'd, not left dangling), and a tampered one is rejected (400) before touching the database at all.

The exact same webhook delivery, replayed a second time: still 200 (Razorpay expects an ack, not a retry-provoking error), the topic's high-watermark unchanged — no duplicate payment.success. The atomic conditional UPDATE (tryResolve) is the actual mechanism; the DB-level unique constraint on razorpay_payment_id, confirmed present directly against Postgres, is a backstop against a different failure — the same id ever attaching to two different orders — not the primary guard.

After all the Razorpay work landed, placed a plain wallet order again: still CONFIRMED synchronously in the same response, razorpayOrderId/razorpayKeyId both null. Every payment.success/payment.failed payload now carries a method field so order-service's new consumer can tell the two paths apart — confirmed the wallet checkout's own event was correctly tagged "WALLET", not just that the filter code looks right.

The webhook controller takes @RequestBody as a plain String instead of a typed DTO like every other endpoint in the project — why the inconsistency?
Because Razorpay signs the literal bytes it sends over the wire, not an abstract representation of the data. If Spring deserialized the body straight into a Java object, verifying the signature would mean re-serializing that object back into JSON to compute the hash — and a re-serialized JSON tree is not guaranteed to produce byte-identical output to what was originally sent (key ordering, whitespace, and number formatting can all differ even when the data is semantically the same). A signature computed over the wrong bytes either fails to verify a genuine webhook or, worse, could theoretically be tricked by a payload where the parsed-and-reserialized form doesn't correspond to what a signature check would actually be validating. Capturing the raw string first and verifying against exactly that removes the whole class of ambiguity — parsing only happens after the signature is already confirmed trustworthy.
Razorpay's servers can't possibly know Vicinia's internal secret — so how does the webhook pass InternalRequestFilter, which checks for exactly that on every single request?
Because the webhook is routed through api-gateway like everything else in this project — added to public-paths so AuthGlobalFilter skips the JWT check Razorpay could never provide either — and AuthGlobalFilter's own code stamps X-Internal-Secret onto every proxied request unconditionally, before it even branches on whether the path is public. That stamping was written for a completely different reason back in Stage 1 — letting the gateway itself vouch for traffic it's already proxying — but it turns out to already solve this problem too, for free. The lesson worth keeping: before adding a special case to a shared security component, check whether the existing design already covers the new scenario by a mechanism nobody built specifically for it.
Inventory reservations, coupon usage, wallet pay, wallet refund, and now Razorpay webhook resolution all use the exact same "conditional UPDATE, check rows-affected" shape — is that just a habit, or is something deeper going on?
It's the same underlying problem showing up five times, not five separate decisions to reuse a trick. Every one of these is "some concurrent or repeated event must transition a row from one state to another exactly once, and the database itself — not application code reading-then-deciding — has to be the thing that enforces that." Reservation count, coupon usage count, wallet balance, and a webhook's resolution status are all, structurally, the same kind of fact: a value that must never be double-mutated no matter how many callers race for it or how many times the same request gets retried. Recognizing that a new problem is actually the same shape as one already solved — rather than reaching for a new mechanism each time — is what let this stage's idempotency requirement get built with total confidence in the pattern's correctness, already proven four times over.
Without a live, publicly-reachable webhook, isn't this just testing against a payload written to pass, rather than against Razorpay's real behavior?
Only if the code under test somehow knew it was being tested — it doesn't. RazorpayPaymentService.handleWebhook has no idea whether the bytes it receives came from Razorpay's servers or from a locally-run Python script; it only knows how to compute an HMAC-SHA256 digest over whatever bytes arrived and compare that against whatever signature header arrived. That computation is entirely deterministic and entirely specified by Razorpay's own public documentation — there's no secret Razorpay-side logic being approximated or guessed at. The one thing genuinely not exercised is Razorpay's own decision about *when* to fire the webhook and with *what* payload shape for a real payment attempt — everything downstream of "a signed payload arrived" is exercised exactly as it would be in production, including the one direction — a tampered signature — that a live webhook test would have no reliable way to trigger on demand anyway.
