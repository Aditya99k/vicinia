Why it works

order-service's delivered() method has reached the terminal DELIVERED status since Stage 11 — but nothing ever described that fact to anyone downstream. Added OrderEventPublisher.publishDelivered(orderId, merchantId, totalAmount), fired the same way as every other terminal transition in this service: save the row first, publish the already-committed state after, never inside a transaction.

5% commission, BigDecimal with RoundingMode.HALF_UP at scale 2 — the exact same rounding convention coupon-service's discount math used in Stage 7. ARCHITECTURE.md §4.7 works through a ₹500 → ₹25 commission → ₹475 net example by hand; a live ₹40.00 order in this stage's own testing produced ₹2.00 commission and ₹38.00 net — the identical 5% ratio, confirmed against a real delivered order rather than only a unit test.

Every orchestration service so far — order-service since Stage 8, delivery-service and merchant-service in Stage 11 — deliberately avoids @Transactional, because the doctrine exists to keep an external call (a Kafka publish, another service's REST call) out of a transaction boundary that might still roll back. SettlementService.runBatch() makes no external call at all: it creates one Payout and links every one of a merchant's PENDING entries to it in a single atomic multi-row Postgres write. That's exactly the case @Transactional exists for — and the first place in this project where the no-transactions doctrine's own stated reason simply doesn't apply, so it's used, and says so in its own Javadoc.

PayoutBatchJob runs on the architecture doc's own "e.g. daily" cadence, grouping PENDING entries into Payouts. PayoutProcessor ticks every 30s, moving PENDING → PROCESSING the moment it sees a fresh payout, then PROCESSING → PAID once a configurable delay (60s in dev) has actually passed — so PROCESSING is a real, observable state, not a value that flips to PAID on the very next tick regardless. Both jobs also have on-demand admin endpoints, for ops (or this project's own testing) that don't want to wait on the schedule.

  • A real order was walked through checkout → merchant accept/ready → delivery assignment → partner accept/pickup/deliver → DELIVERED, producing a real ledger entry (₹40.00 gross / ₹2.00 commission / ₹38.00 net, PENDING).
  • Admin run-batch grouped it into a ₹38.00 Payout — the net amount, since that's what the merchant actually receives, not the gross the customer paid.
  • Left alone with no further action, the scheduled PayoutProcessor advanced it PENDING → PROCESSING → PAID entirely on its own within the configured window.
  • A genuine settlement.completed message showed up on settlement-events with the correct payout ID, merchant ID, and amount — fired at the real PAID transition, not a mock event created eagerly alongside the payout.
notification-service's idempotency test in Stage 12 replayed the exact same eventId — why does this stage's test deliberately use a different, hand-crafted eventId for the same order instead?
Because it proves a stronger claim. Replaying an identical eventId only shows that redelivering the exact same Kafka message doesn't duplicate — useful, but it leaves open whether the guard is actually checking "has this order already been settled" or just "have I seen this exact message before," which are different questions with different failure modes. A hand-crafted event with a fresh eventId but the same orderId forces the check to prove it's keyed on the real business fact (existsByOrderId), the way it would have to be to survive a genuinely different bug elsewhere — say, a producer accidentally publishing order.delivered twice for the same order with two different eventIds. A financial ledger is exactly the place where "probably fine" idempotency isn't good enough to leave unproven.
Each SettlementEntry stores gross, commission, and net separately — why does the batch job sum the net figures into the Payout rather than the gross ones?
Because a Payout answers one specific question: how much money actually moves from the platform to the merchant's bank account. The platform keeps the commission — it was never the merchant's money to begin with, just the customer's payment passing through on its way to being split. Summing gross into the payout total would mean the simulated "bank transfer" claims to send the merchant money that includes the platform's own cut, which isn't what a payout represents in any real settlement system. gross/commission stay on each individual SettlementEntry as the audit trail of how that number was derived; net is the only figure that belongs in the number actually paid out.
The processor ticks every 30s — why not just make PROCESSING last exactly one tick, instead of adding a separate 60s processing-delay setting to check against?
Because if PROCESSING always lasted exactly one tick, it would never be a state anyone could actually observe or query against — it would always have already moved on to PAID by the time any request asked about it, making the "three real states" claim from ARCHITECTURE.md's own reasoning technically true but practically meaningless. Separating the tick cadence (how often the job checks) from the processing delay (how long a payout genuinely sits in PROCESSING) means PROCESSING is a real window a merchant's own /payouts/mine call, or an admin's /admin/payouts listing, can actually catch mid-flight — the same distinction between "how often something is checked" and "how long a thing actually takes" that a real bank transfer has, simulated faithfully rather than collapsed away for convenience.
