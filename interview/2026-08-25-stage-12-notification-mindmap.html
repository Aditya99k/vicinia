Why it works

Stage 11 needed a pulled-forward slice of merchant-service before it could even start. Stage 12 didn't — user.registered, order.confirmed, payment.failed, and inventory.low all already had real producers from earlier stages. notification-service is purely a new listener on existing plumbing: 4 consumer groups, one per topic, each filtering to exactly the single eventType ARCHITECTURE.md §7's table names for it — every one of those 4 topics also carries other event types this service deliberately ignores.

No real email or SMS provider is wired up — BUILD_TRACKER.md's own checklist item says "email send (or logged-only stub if no real provider wired)." LoggingNotificationSender is that stub: it logs at INFO as the actual send mechanism, sitting behind a NotificationSender interface. A real provider later is a new implementation of that interface, not a change to NotificationService or any of the 4 consumers.

ARCHITECTURE.md §11 prefers a state-check before mutating over a separate processed_events table. Every other consumer in this project checks its own business state (is the order still PAYMENT_PENDING, does the profile already exist) — here, the "business state" is the notification log itself, so existsByEventId against the same collection NotificationService.record() writes to is the natural fit, not a workaround.

  • auto-offset-reset: earliest (deliberate — a brand-new consumer group should backfill everything already on these topics, same call delivery-service made in Stage 11) meant the very first boot processed the entire existing history across all 4 topics.
  • 63 notifications materialized on first startup: 38 user.registered, 14 order.confirmed, 9 inventory.low, 2 payment.failed — content read correctly against real historical orders and products from every earlier stage's testing.
  • db.notifications.distinct("eventType") confirmed only those exact 4 types ever got a record — no order.created, payment.success, or inventory.out leaked through the per-consumer filters.
  • A fresh live order placed afterward produced a 5th order.confirmed notification with a correctly populated recipientUserId, confirming the backfill wasn't quietly masking a bug in the current payload shape.

Republished a real, already-processed user.registered event with the identical eventId — document count held at 64, no new log line, confirming the check short-circuits before either the send or the insert. Then reused Stage 10's exact DLQ method: a hand-crafted event with a non-string userId (a nested object, so the parsing cast fails deterministically), which retried 3 times and landed on user-events-notification-service-user-dlt. The same malformed message also independently failed in both of user-events' other real consumer groups — payment-service's wallet auto-provisioner and user-service's own profile consumer — each landing on its own correctly-named DLT with zero cross-contamination, reconfirming Stage 10's naming fix under a genuinely new third consumer group on an already-shared topic.

Each of the 4 topics carries other event types too — why not just notify on all of them, since more visibility seems strictly better?
Because ARCHITECTURE.md's own event table is explicit about which 4 event types this service consumes, and that list isn't arbitrary — payment.success, for instance, is deliberately excluded because a successful payment is already implied by the order.confirmed notification that follows it in the same checkout flow; sending both would just be a duplicate ping for the same real-world moment. Consuming everything a topic happens to carry, rather than the specific signals actually worth notifying someone about, would make the notification log noisy in exactly the way a notification system is supposed to prevent — the discipline of filtering per the architecture's table is the feature, not a limitation to work around.
Isn't relying on historical events from earlier stages a shortcut compared to placing fresh test orders for each of the 4 event types?
It's actually a stronger test than four hand-placed orders would have been, for one specific reason: hand-crafted test events are shaped by what the person writing them expects the payload to look like, while a real backfill contains whatever every earlier stage's testing actually produced — different schema states, different field presences, orders from before and after Stage 11's payload widening, wallet top-ups and Razorpay flows both. If the consumers' payload parsing had any assumption baked in that only held for freshly-created test data, a backfill of 63 real historical events across 5 days of prior work is exactly the kind of messy input that would have exposed it — and did, in the form of the one stale null-recipient record, which turned out to be genuinely old data rather than a live bug, confirmed by placing one fresh order afterward and checking it came through clean.
Every other gated endpoint in this project checks a specific permission like DELIVERY_MANAGE or STORE_MANAGE — why does /api/notifications/mine skip that and rely only on X-User-Id?
Because RBAC permissions in this system gate access to a category of action or data — managing a store, managing deliveries, approving merchants — not access to one's own resources by identity. order-service's /orders/mine works the same way: the JWT already proves who the caller is, and "show me my own notifications" doesn't need a further permission check on top of that, since there's no meaningful distinction between roles here — a customer, a merchant, and a delivery partner all equally deserve to see their own notification history. A permission check would only make sense if some role were meant to be denied their own data entirely, which isn't a real requirement anywhere in this system.
