Why it works

validate is a pure read — checks active/expiry/min-order/per-user-limit and returns the computed discount, never touching usage_count. apply runs the exact same checks and then commits: the atomic increment, plus a CouponUsage row keyed on (couponId, orderId). Confirmed directly: firing validate repeatedly never moves the usage counter.

UPDATE coupons SET usage_count = usage_count + 1 WHERE id = :id AND (usage_limit IS NULL OR usage_count < usage_limit) — rows-affected, not an exception, tells the caller whether it won. ARCHITECTURE.md §6 names this explicitly: "usage-limit enforcement is an atomic-increment-with-check problem, same family as inventory." Same guarantee, same mechanism, different table.

  • Different orders, one limit: usageLimit=1, 20 parallel applies each with its own orderId — exactly one 201, nineteen 409s, final usage_count=1, one usage row. This is the test BUILD_TRACKER's "Done when" actually asks for.
  • Same order, many retries: a second coupon, 15 parallel applies all sharing one orderId — a genuine double-submit race. All 15 return 201 with the identical result; usage_count net-increments by exactly 1, not 15.

First draft handled the same-orderId race the obvious way: plain insert, catch the unique-constraint violation, compensate the increment. Never shipped — under Postgres, any statement error aborts the whole surrounding transaction until an explicit rollback, so every line after that catch block would have failed with "current transaction is aborted." Replaced with INSERT ... ON CONFLICT (coupon_id, order_id) DO NOTHING, which never raises a SQL error at all. The 15-way same-orderId test above exists specifically to prove this path — confirmed clean, zero errors logged.

  • Percentage discount capped by maxDiscountAmount: 20% of 500 → 100, clamped to 50; 20% of 150 → 30, uncapped, both confirmed.
  • Admin create/list/update gated by COUPON_MANAGE — already seeded onto ADMIN since Stage 2, zero RBAC changes needed. Duplicate codes → 409; non-admin → 403.
  • Deactivated coupon, and a coupon with a past validUntil, both correctly rejected on both validate and apply — not just the read path.
  • Direct hit bypassing the gateway → 403; unauthenticated apply → 401.
Java's try/catch caught the DataIntegrityViolationException just fine — why wasn't that enough?
Because catching the exception in Java only stops it from propagating out of the method; it does nothing about the state Postgres itself is now in. Postgres treats any error during a transaction — a constraint violation included — as poisoning the whole transaction, not just the one statement: every following command on that same connection returns "current transaction is aborted, commands ignored until end of transaction block" until an explicit ROLLBACK (or a savepoint) resets it. Spring's @Transactional binds one connection to the whole method call, so the moment the risky insert fails, everything after it in that method — the compensating decrement, the re-fetch of the row that actually won — is doomed regardless of whether the Java-level exception was caught. The fix isn't better exception handling; it's not causing the database-level error in the first place, which is exactly what ON CONFLICT DO NOTHING is for.
If the global usageLimit deserves an atomic UPDATE, why doesn't perUserLimit get the same treatment?
Because the two limits protect against genuinely different threat shapes. usageLimit protects against many different customers all racing for one scarce resource at the same instant — a real, common, high-stakes scenario (a flash-sale code going out on a notification blast) that specifically needs a hard, database-enforced guarantee. perUserLimit protects against one customer racing themselves — which requires that same customer to fire multiple simultaneous requests for the same coupon, a rare and low-consequence edge case even when it happens (worst case, one user gets one extra use of their own coupon, not a coupon meant for a thousand people getting consumed by ten). Test (1) actually demonstrates both mechanisms working together correctly: of 19 rejected requests, most were caught by the ordinary sequential per-user check, and exactly the 2 that raced past it in time were caught by the atomic increment — the hard guarantee exists precisely to backstop the cases the softer check can't reach in time.
The atomic UPDATE already stops the global count from ever going over the limit — doesn't that make the coupon safe regardless of retries?
It stops the count from exceeding the limit, but not from silently drifting upward on every retry of the same logical request — a network blip that causes a client to resend the same "apply this coupon to this order" call would otherwise count as two separate uses of a coupon that should only ever count once. The unique (couponId, orderId) constraint is what answers a different question than the atomic UPDATE does: not "is there room for one more use" but "have I already recorded this exact use." Both guarantees are needed together — one bounds the total, the other makes each legitimate use count exactly once no matter how many times the same request is retried.
Every service so far has needed at least one thing from another service — Kafka, a REST call, something. Why does coupon-service have none of that?
Because ARCHITECTURE.md §7's own dependency table lists nothing for it — no Kafka topic produced or consumed, no synchronous call out to another service. A coupon's validity depends only on facts coupon-service already owns outright: its own active flag, its own expiry window, its own usage counts. Compare that to inventory-service, which had to ask catalog-service "does this product exist," or cart-service, which had to ask inventory-service "what does this cost right now" — those services needed an external source of truth for something they didn't own. Coupons don't reference anything outside themselves to decide whether they're valid, so there's genuinely nothing to wire up. Simplicity here isn't a shortcut — it's what a self-contained bounded context looks like when the boundary is drawn correctly.
