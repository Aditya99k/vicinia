Why it works

frontend/customer-app — Vite + React 19, react-router-dom, axios. Blinkit-inspired: bold saturated yellow as the one accent color, near-black text, rounded cards, a centered phone-frame shell on desktop. Poppins for anything confident (headings, buttons), DM Sans for body copy.

why not fake the merchant/catalog screens tooStage 3+ hasn't been built yet. Faking a product grid would make the app look more finished than the backend actually is — the Home page's "Stores near you" section is an explicit, honestly-labeled placeholder instead, naming exactly which stage unlocks it.
  • Signup and login, with a role picker matching auth-service's actual self-registerable roles.
  • "Forgot password?" walks through the real flow — including a plain instruction to go read the reset token out of logs/auth-service.log, since notification-service doesn't exist until Stage 12. No pretending an email got sent.
  • AuthContext + one localStorage JSON blob (src/api/storage.js) holding the whole AuthResponse shape — tokens, roles, permissions — set once on signup/login, read everywhere else.

Home shows RBAC roles/permissions as literal chip counts (a playful way to prove the JWT claims actually made it to the browser), the default address if one exists, and a "setting up your profile" banner with a manual refresh button if the profile 404s right after signup — because user-service creates it asynchronously off the user.registered Kafka event, and that can take a beat.

Addresses is full CRUD against user-service: a bottom-sheet form for add/edit, delete with a confirm, a default badge — genuinely exercising every endpoint in that controller, not just the read path.

api-gateway had zero CORS configuration — every test of it so far (Postman, curl) doesn't enforce same-origin rules the way a real browser does, so this was invisible until an actual browser tab tried to call it from http://localhost:5173. Fixed with spring.cloud.gateway.globalcors scoped to that exact origin, plus an explicit OPTIONS short-circuit added to AuthGlobalFilter as defense-in-depth — a CORS preflight request carries no Authorization header by design, and the filter would otherwise have read that as an unauthenticated request to a protected path and rejected it with 401, breaking every real request before it could even happen.

why this is a good lesson beyond ViciniaA backend that only gets tested with API clients (curl, Postman) can silently never notice it doesn't work from an actual browser — CORS is enforced by the browser itself, not by the server refusing requests outright. The only way to actually catch it is to test from something that behaves like a browser, or explicitly simulate the preflight.
  • npm run build and mvn clean install both pass clean.
  • A real OPTIONS preflight against /api/auth/signup with Origin: http://localhost:5173 returns 200 with the correct Access-Control-Allow-* headers.
  • A real signup and profile fetch, both with an Origin header attached to simulate exactly what the browser sends, both succeed with CORS headers present.
  • Only after that did the app actually get opened in a browser — the API layer's correctness was established first, independent of whatever the UI looks like.
Why does the browser send an OPTIONS request before the real POST?
For any cross-origin request that isn't a "simple" one (has a JSON body, a custom header like Authorization, uses PUT/DELETE...), the browser first asks the server, via an OPTIONS request carrying Origin and Access-Control-Request-* headers, "would you actually allow this?" — before it ever sends the real request with real data. Only if the server answers with matching Access-Control-Allow-* headers does the browser proceed to send the actual request at all.
Why is this enforced by the browser and not the server?
The server was always able to receive the request — CORS is entirely a browser-side protection for the user, stopping a malicious page at evil.example from silently making authenticated requests to your-bank.example using the victim's existing cookies/session. A non-browser client (curl, Postman, another backend service) was never subject to it in the first place — which is exactly why testing only with those tools never surfaced this gap.
What actually goes wrong without the dedup?
If Home's profile fetch and addresses fetch both fire around the same time and the access token happens to be expired, both would 401 independently and — without coordination — both would call /api/auth/refresh separately. Refresh tokens rotate on use (§Day 2): the first call succeeds and consumes it, the second call arrives a moment later presenting the now-already-consumed token and gets rejected, logging the user out even though nothing was actually wrong.
How does one shared promise fix that?
The first 401 to arrive creates the refresh Promise and stores it in a module-level variable; every other 401 that arrives while it's still pending just awaits that same promise instead of starting a new request. Only one /refresh call ever goes out no matter how many requests failed around the same moment, and every failed request resumes with the one new access token once it resolves.
Why not just retry silently in the background until the profile shows up?
A silent retry loop would work, but it would also hide a genuinely interesting fact about the system from anyone watching: profile creation is asynchronous, driven by a Kafka event, not a direct side effect of signup. Showing the pending state with a short explanation turns a would-be-invisible implementation detail into a small, honest window into how the backend actually behaves — useful for exactly the kind of validation this app exists for.
