Why it works

First MongoDB-backed service in the monorepo — Product and Category as @Document entities via Spring Data MongoDB, not JPA. Product carries name, brand, category, description, image URLs, a free-form attributes map, and a status, but deliberately no merchantId — see Deep Dives for why.

why a document store here, when every other service so far is PostgresProduct attributes genuinely vary by category — a fruit has a unit and a shelf life, a phone has a spec sheet — so a rigid relational schema would mean either a wide sparse table or an EAV workaround. A schemaless document per product with a flexible attributes map fits the actual shape of the data (ARCHITECTURE.md's stated reasoning for MongoDB here), and there's no cross-product relational query this service actually needs.
  • GET /api/catalog/products/search — optional name/category filters, four-way branch in CatalogService.search(...), always scoped to status = APPROVED only.
  • GET /api/catalog/categories — the full category list, seeded once at boot by CategorySeeder (8 categories, matched to the glyphs already on the frontend's home page).
  • Both are public — no JWT required — since browsing a storefront has to work before a customer ever logs in.

Two ways a product enters the catalog: an admin creates one directly (auto-APPROVED, immediate), or any authenticated user requests one via POST /products/request (lands as PENDING_REVIEW, invisible to search, tied to requestedByUserId from the gateway-injected X-User-Id). Admins see the queue at GET /admin/products/pending and resolve each one with approve or reject (with a reason) — gated by the new CATALOG_MANAGE permission.

Published to product-events, partitioned by productId, via the same EventEnvelope pattern as every other service's events so far. Fires exactly once per product — on the transition into APPROVED, whether that happened instantly (admin-created) or after a review cycle (merchant-requested then approved) — and specifically not on rejection, since a rejected product never becomes real inventory-eligible catalog data.

  • api-gateway's public-paths still had Stage 1's placeholder /api/catalog/** — would have exempted the new admin/merchant-protected catalog endpoints from JWT validation entirely. Narrowed to the two genuinely-public paths.
  • RoleSeeder only ran its upsert once (if (roleRepository.count() > 0) return) — the new CATALOG_MANAGE permission would never have reached ADMIN on the already-seeded database. Changed to an idempotent per-role/per-permission upsert that runs every boot.
  • A third service now needed the exact same permission-header-parsing logic already duplicated in merchant-service — extracted into common.security.PermissionUtil, with each service keeping a thin wrapper for its own exception type.

Also stood up MongoDB in docker-compose.infra.yml, self-hosted for now — see Deep Dives for why that's not a deviation from the deployment plan.

  • Public categories/search work with no token; unauthenticated write → 401; gateway-bypass direct hit on the service's own port → 403.
  • Admin-created product → auto-APPROVED, immediately in search; unknown category → 400.
  • Non-admin (no CATALOG_MANAGE) on an admin endpoint → 403.
  • Merchant request → PENDING_REVIEW, absent from search, visible in the admin pending queue and the requester's own /mine.
  • Admin approve → APPROVED, now in search, product.created actually consumed off Redpanda to confirm it — not just assumed sent.
  • Re-approving an already-approved product → 409, illegal transition correctly rejected.
  • Reject flow with a reason → REJECTED, stays out of search, confirmed no event published for it.
  • Admin category creation → 201; duplicate name → 409.
Real merchants sell real products — why isn't the merchant tied directly onto the product record?
Because "a product exists" and "merchant X stocks this product at price Y with quantity Z" are genuinely two different facts with two different lifecycles (ARCHITECTURE.md §4.2). The same 500ml carton of milk is one catalog entry no matter how many merchants sell it — modeling it as one Product per merchant would mean duplicate near-identical documents the instant a second store starts stocking the same item, and no way to ask "who sells this" without a fragile text match across duplicates. The per-merchant fact — price, stock, availability — is exactly what Stage 5's inventory-service exists to own, as a MerchantListing that references a productId. Catalog stays the shared, merchant-agnostic truth; inventory is where merchant-specific reality lives.
A seeder that only runs when the table is empty sounds like the normal, safe pattern — why was that wrong here?
It's the right pattern for data that's genuinely fixed at first boot and never changes again. Roles and permissions aren't that — this project adds a new permission (CATALOG_MANAGE, and eventually more, per stage) every time a new domain service gets an admin surface, against a database that's already been seeded once, weeks earlier, in a prior stage. A guard of "only seed if the table is empty" silently freezes the permission set at whatever it was the first time the service ever booted — every later addition to the seeder's source code becomes dead code against any environment that already exists. An idempotent upsert (find-or-create each role, find-or-create each permission, grant it) costs nothing extra on a truly first boot and is the only version that's actually safe to keep editing over the life of the project.
The wildcard /api/catalog/** was already there from Stage 1 and nothing was broken — why go back and change it?
Because it was written before catalog-service's real endpoints existed, as a stand-in guess, and stand-in guesses need to be revisited once the real shape is known — not left in place by inertia. At Stage 1 there was no distinction between "browse a product" and "moderate a product" to get wrong yet; by Stage 4 there is, and a route-level wildcard can't express it. Left unfixed, POST /api/catalog/admin/products/{id}/approve would have matched the same public-path pattern as GET /api/catalog/products/search, meaning anyone — no token, no role, nothing — could have approved or rejected catalog listings directly. It never got exploited because it was caught during this stage's own wiring, before the first functional test even ran, but it's exactly the kind of gap that's invisible until someone specifically checks what a wildcard actually matches against a service's full real route table.
DEPLOYMENT.md says even local dev should point at a real Atlas cluster — doesn't self-hosting Mongo in Docker contradict that?
Only if it were meant to stay that way. BUILD_TRACKER.md scopes standing up the real managed infrastructure — Atlas included — to Stage 20, deliberately after every service that needs a database has already been built and proven against a local equivalent; building catalog-service in Stage 4 shouldn't be blocked on an external account signup that was never scheduled to happen for another sixteen stages. The connection string is the only thing that changes: MONGODB_URI defaults to the local container now and swaps to a real mongodb+srv:// Atlas URL later with zero code changes in catalog-service itself — the same pattern already used for every other secret in this project.
Eureka's own registry showed CATALOG-SERVICE as UP, and hitting it directly worked — so what was actually 503-ing through the gateway?
A different, closer cache: Spring Cloud LoadBalancer keeps its own client-side list of known-good server instances per service, separate from Eureka's server-side registry, and only refreshes it periodically rather than on every single request. Right after catalog-service first registered, the gateway's registry-server view already had it — but the gateway's own load-balancer cache hadn't picked that up yet, so lb://CATALOG-SERVICE briefly had nowhere to route to. The same shape of gap showed up a second time this session, larger, after the dev machine woke from sleep — a real elapsed-time gap long enough for a missed Eureka heartbeat and a re-registration cycle, which is visible directly in api-gateway's own log timestamps. Both times a plain retry a few seconds later resolved it cleanly, with no code change — the fix isn't a fix, it's recognizing that a load-balancer's local cache lagging its source of truth by a few seconds is expected behavior, not a defect, and exactly why start-infra.sh's own Eureka-registry-snapshot step already retries in a loop rather than checking once.
