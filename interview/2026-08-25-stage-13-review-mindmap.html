Why it works

BUILD_TRACKER.md's own checklist item says "gated... via Feign to order-service" — but Feign has never actually been used anywhere in this codebase. Every internal call so far (cart→inventory, order→coupon/inventory/payment/cart, inventory→catalog) uses a `@LoadBalanced RestTemplate` with an interceptor that stamps `X-Internal-Secret` automatically. review-service's new `OrderClient` follows that exact convention rather than introducing a second HTTP client abstraction for one call.

GET /api/orders/internal/delivered?userId=&productId= sits under order-service's existing /api/orders prefix, gated purely by InternalRequestFilter's secret check — no separate "internal-only" URL scheme, matching InternalPaymentController's and ReservationController's precedent exactly. Backed by one derived query, existsByUserIdAndStatusAndItems_ProductId, traversing the already-existing Order → OrderItem relation — no new table, no denormalized copy of order history anywhere.

One review per (userId, productId), enforced by an actual MongoDB compound unique index — a pre-check still runs first for a clean 409 on the normal path, but the index is what actually closes the race window, caught via DuplicateKeyException. Mongo's auto-index-creation defaults to off in Spring Data MongoDB — catalog-service's own @Indexed(unique = true) fields from Stage 4 never explicitly turned it on either, an existing gap left alone here — so it was set explicitly for review-service, and verified directly with db.reviews.getIndexes() that the index actually exists, not just assumed from the annotation.

The rating endpoint runs a live MongoDB aggregation ($match → $group with $avg/$count) rather than maintaining a running average on the product. ARCHITECTURE.md's own description of this collection — "read-heavy... no cross-entity transactions" — is exactly the profile where a stored aggregate's drift risk costs more than the aggregation's runtime cost.

  • A fresh customer with zero orders tried to review a real product first — 403, ReviewNotEligibleException.
  • That same customer was walked through a genuine order — wallet top-up, cart, checkout, merchant accept/ready, delivery-service assignment, partner accept/pickup/deliver — reusing Stage 11's own merchant and delivery-partner accounts, to a real DELIVERED status.
  • The identical review request that had 403'd now returned 201. A second identical request 409'd.
  • A second, independent reviewer succeeded too — using a delivered order from Stage 11's own testing, days old, never touched for this test — and the rating aggregate correctly read {averageRating: 4.0, reviewCount: 2} across ratings of 5 and 3.
  • A product with no reviews at all returned {averageRating: 0.0, reviewCount: 0} cleanly, not an error or a NaN.
It would have been simpler to just place a second fresh order for the second reviewer too — why deliberately reach for a Stage 11 order instead?
Because a freshly-placed order proves the code works against data shaped exactly the way this test's own setup shaped it — the same customer session, the same moment, the same code paths that just ran. Reusing a real order from an entirely different testing session, built for an entirely different stage's purposes days earlier, proves something a fresh order can't: that the delivered-order check works against order history it had no hand in creating, the way it actually will in production against real, pre-existing purchase history. If the eligibility query had any hidden assumption tied to how orders get created in this specific test run, an old, unrelated order is exactly the kind of input that would have broken it.
Real review systems usually let you edit or update your review — why does this one just reject a second attempt outright with a 409?
Because BUILD_TRACKER.md's own "done when" bar for this stage is narrow and explicit: a review can only be created after a delivered order, and the rating aggregate updates correctly. It says nothing about editing, and adding an update flow now would be building for a requirement that hasn't actually been asked for — the kind of premature scope expansion that tends to produce half-designed features nobody asked for yet. One review per (userId, productId), enforced by a real unique index, is the complete, correct shape for what this stage actually requires; an edit endpoint is a real, separate feature for whenever it's actually needed, not a gap in this one.
Every customer-facing endpoint in this project reads the caller's identity from an X-User-Id header set by the gateway — why doesn't order-service's new internal endpoint follow that same pattern?
Because X-User-Id in this system always means "the authenticated caller of this specific request," stamped by api-gateway from a verified JWT — it identifies who is asking. This internal call is a different shape entirely: review-service isn't acting as the reviewer, it's asking order-service a factual question about an arbitrary third party's purchase history, on review-service's own authority as a trusted internal caller (proven via X-Internal-Secret, not a JWT belonging to that user). Passing userId as an ordinary query parameter — the same way CouponClient passes a code and an amount as plain request data — keeps that distinction clear: the header answers "who's calling," the parameter answers "who's the call about," and conflating the two would misrepresent what's actually being asked.
