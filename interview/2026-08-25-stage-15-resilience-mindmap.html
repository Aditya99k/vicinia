Why it works

@Retryable (Spring Retry — already a dependency since Stage 10's Kafka @RetryableTopic) handles the two idempotent-only retries: InventoryClient.reserve() and PaymentClient.payWithWallet(), scoped to genuine transient failures only, never the 402/409 business rejections those methods already handle. resilience4j-spring-boot3 (a new dependency) handles @CircuitBreaker + @Bulkhead on createRazorpayOrder() alone — deliberately not retried, since minting a second Razorpay order isn't an idempotent operation to retry blindly.

Widened order-service's own management.endpoints.web.exposure.include to add circuitbreakers/circuitbreakerevents — and it silently didn't take effect. Config Server's shared application.yml sets the same key, and a remote property source imported via spring.config.import takes precedence over the importing service's own local file. Fixed with config-repo/order-service.yml — the first per-service override this project has actually needed, exactly the mechanism the shared file's own top comment predicted years of stages ago.

  • Pointed RazorpayClient's hardcoded URL at an unreachable host, rebuilt and restarted only payment-service — the wallet path stayed genuinely untouched, isolating "Razorpay is degraded" from "payment-service is down," the real-world scenario this pattern exists for.
  • Repeated Razorpay checkouts drove /actuator/circuitbreakers from CLOSED to OPEN once the failure-rate threshold crossed — notPermittedCalls climbing as later calls were rejected without even attempting the network call.
  • Watched it auto-transition to HALF_OPEN after the wait duration, reopen when trial calls still failed (URL still broken), then — after reverting the URL — close back to CLOSED on 3 successful trial calls.
  • Every state in the machine, confirmed against the real running JVM, not inferred from the annotation being present.

While the razorpay circuit sat open, a wallet order with sufficient balance completed in 0.25s at CONFIRMED — completely unaffected. Razorpay-path attempts during the same window failed in well under 0.1s each, a clean 503 via the new PaymentGatewayUnavailableException. This is the actual claim BUILD_TRACKER.md's "done when" makes — not "the annotation compiles," but "wallet-only customers never notice."

Killing the tracked PID (the mvn spring-boot:run wrapper, not its child JVM) left the real java process running — the "outage" wasn't real. Killing the wrapper with a graceful signal deregistered the instance from Eureka correctly, but produced IllegalArgumentException: Service Instance cannot be null — a load-balancer-level failure, correctly not retried (no instance exists to retry against). kill -9 on the actual child JVM PID finally produced the real scenario: Eureka still reporting the instance UP while its port is genuinely dead. That request took 1.68s — matching 3 attempts across the configured 500ms/1000ms backoff — before failing with ResourceAccessException: ... Connection refused, the exact retryable type, confirmed in the logs.

60 sequential curl calls all returned 200 — the token bucket (20/s replenish) simply refilled between each one, never actually running dry. 80 truly concurrent requests (xargs -P 40) told the real story: 60×200, 20×429, matching the configured burst-plus-replenish math exactly. A different user's request succeeded immediately while the first user's bucket sat exhausted, confirming per-user isolation; the same burst against a public, unauthenticated endpoint produced a clean 40×200/40×429 split — the IP-based fallback for paths with no X-User-Id yet.

Resilience4j and Spring Retry are well-established libraries — wouldn't a correct annotation with correct config just work, without needing to actually crash three services to prove it?
The libraries themselves are trustworthy; the question this stage actually needs answered is whether *this specific application's wiring* of them is correct — and that's exactly where the real bugs in this session showed up, none of which were library defects. The actuator endpoint silently missing wasn't resilience4j's fault, it was Config Server's precedence rules. The first two retry tests silently not firing weren't Spring Retry's fault, they were about which PID actually got killed and what exception type Eureka's load-balancer throws when an instance disappears entirely versus when it just stops responding. None of those are things a code review of the annotations would have caught — they only showed up by actually triggering the failure and watching what happened, the same lesson Stage 10's DLQ testing already taught this project once.
Since a failed Razorpay call was already being deliberately triggered to test the circuit breaker, and it was already known that the order gets stuck with inventory still reserved — why not just add the cleanup while already in that code?
Because fixing it well requires a real design decision this stage isn't the place to make casually: should a failed Razorpay-order-creation auto-release the reservation and mark the order failed immediately, or should the customer be allowed to retry Razorpay specifically since the reservation is still valid and there's no reason to force them back through checkout entirely? Those are different UX and correctness tradeoffs, and picking one under time pressure while verifying an unrelated stage would be exactly the kind of undersized, unreviewed fix that creates a second problem while solving the first. Stage 15's job was proving the resilience patterns work — noting the gap precisely, with the evidence that surfaced it, is what lets a future stage make that design decision properly instead of inheriting an undocumented one.
"Isolated from internal-service calls" sounds like it should mean a genuinely separate thread pool for Razorpay calls — why does the actual implementation use a semaphore that still runs on the caller's own thread?
A thread-pool bulkhead is the more literal reading, but it requires the annotated method to return CompletableFuture, reshaping createRazorpayOrder's calling contract and adding real complexity (executor sizing, async error propagation) for a synchronous checkout flow that just needs the result before continuing. A semaphore bulkhead achieves the concern that actually matters here — capping how many of Tomcat's own request threads can be simultaneously blocked inside a slow Razorpay call — without changing the method's shape at all: past the configured limit, calls fail fast with a clear error instead of queuing or blocking further, which is the behavior that protects the pool wallet-only checkout depends on. The literal "separate thread pool" reading isn't wrong, it's just solving a problem — moving execution off the request thread entirely — that this specific call site, being synchronous end to end, doesn't actually have.
