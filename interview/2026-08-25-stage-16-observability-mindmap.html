Why it works

13 domain services are traditional Servlet/thread-per-request apps, where ThreadLocal-based MDC works natively — one shared CorrelationIdFilter in common covers all of them. api-gateway is WebFlux, where a single request hops across multiple event-loop threads, so a ThreadLocal doesn't reliably follow it — it gets its own CorrelationIdGlobalFilter instead, which generates/propagates the header correctly but deliberately logs its own line explicitly rather than chasing full Reactor-Context MDC propagation for a concern (gateway's own internal logs) that isn't what the cross-service requirement actually needs.

A raw Kafka ProducerInterceptor, wired purely through spring.kafka.producer.properties.interceptor.classes in each service's application.yml — no publisher class anywhere touched — copies MDC onto every outgoing record as a real header. On the way in, a Spring Kafka RecordInterceptor (not the raw ConsumerInterceptor SPI, which only sees whole batches before Spring's own container dispatches individual records) reads it back immediately before each record reaches its @KafkaListener method.

micrometer-registry-prometheus went into common's own pom exactly once — every one of the 14 services that already depends on it gets a working /actuator/prometheus endpoint the moment prometheus is added to their exposure list, no per-service dependency edits needed. Only discovery-server and config-server — the two services with no common dependency at all — needed it declared directly.

api-gateway's own local application.yml has set management.endpoints.web.exposure.include: health,info,gateway since Stage 1 — and it's been silently losing to Config Server's shared, narrower default this entire time, the exact bug fixed for order-service in Stage 15. Nobody noticed because nothing ever depended on /actuator/gateway until now. Fixed with config-repo/api-gateway.yml, restoring the endpoint and adding prometheus alongside it.

Micrometer's usual meterRegistry.counter(name, tags).increment() pattern only registers a counter on its first increment — so an oversell canary that (correctly) never fires would simply never appear in /actuator/prometheus at all, indistinguishable from "no data yet" on a dashboard built to say "this should read zero." Fixed by registering the Counter eagerly in InventoryService's constructor instead — confirmed live: inventory_oversell_total 0.0, present from the moment the service boots.

Mounting the dashboard JSON directory as a second, separate read-only volume — nested inside the already-mounted, also-read-only provisioning/ parent — failed outright on container start: Docker can't create a mountpoint inside a directory a different volume already owns read-only. Fixed by moving the JSON files into the existing provisioning/dashboards/json/ tree and mounting the whole provisioning/ directory exactly once.

  • A hand-set X-Correlation-Id sent through a real signup → wallet top-up → cart → checkout flow.
  • Found in 8 services' logs afterward — api-gateway, auth, cart, merchant, order, payment, notification, user — double the required 4.
  • Two of those hops (merchant-service's OrderConfirmedConsumer, notification-service's listeners) only ever received the ID via a Kafka message, proving the header-propagation path, not just the synchronous HTTP one.
  • All 16 Prometheus scrape targets confirmed up; all 5 Grafana dashboards confirmed loaded via the API and queried directly against Prometheus using each panel's own exact PromQL — real, non-empty data on every one.
A single request to one endpoint with the header set would have proven the gateway-to-service propagation — why run a whole multi-step checkout instead?
Because the actual claim being verified isn't "the gateway can set a header" — it's "one customer's action can be followed through this system's logs no matter which mechanism carried it forward," and this system has two genuinely different mechanisms: a synchronous HTTP call (gateway to order-service directly) and an asynchronous Kafka hop (order-service publishing, merchant-service and notification-service consuming later, on their own threads, in their own consumer groups). A single curl to one endpoint only ever proves the first path. Only a flow that naturally produces both — sign up (fires a Kafka event notification-service consumes), then check out (fires another event merchant-service and notification-service both consume) — can prove the header actually survives the trip through a topic and back out into a completely different service's MDC, which is the harder, more failure-prone half of the requirement.
Micrometer supports an @Timed/@Counted-style annotation approach — why hand-place every counter.increment() call at a specific line instead of just annotating the methods?
Because an annotation on a method counts "this method was called," which isn't the same claim any of these 5 dashboards actually make. The order funnel needs to know specifically when an order became CONFIRMED, not every time markConfirmed() the private helper happens to run — the same is true of the payment-outcome counter, which has to fire exactly once per real success or failure across two entirely different payment paths that share nothing but a common publisher method. An annotation would either double-count internal helper calls or miss the actual business event the panel is meant to plot. Placing each increment by hand, at the exact line where the business fact becomes true, is what makes "this dashboard renders real data" actually mean the real thing, not an approximation of it.
This project already has Eureka wired into everything else — why does Prometheus's scrape config hardcode 16 host:port pairs instead of using Prometheus's own Eureka service-discovery integration?
Because every real app service in this project runs on the host machine via mvn spring-boot:run, while Prometheus itself runs inside Docker — meaning whatever address Eureka SD resolved instances to would still need translating across that same host-vs-container boundary before Prometheus could actually reach it, adding a layer of indirection that doesn't remove the host.docker.internal problem, just moves it somewhere harder to see. A static list of 16 known, stable ports is simpler, fully deterministic, and trivially easy to verify by reading the file — the same "boring but reliable" call this project has made before, favoring a DB-polling reaper over a fancier event-driven alternative elsewhere in the architecture.
