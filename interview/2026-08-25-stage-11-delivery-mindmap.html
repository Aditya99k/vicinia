Why it works

Stage 11's own job — assign a delivery partner to an order that's READY_FOR_PICKUP — presupposes an order.ready event, but nothing in the system produced one. merchant-service had never had an accept/prepare/mark-ready capability at all; it just hadn't come up yet, since order-service's own transition guard was built ahead of its own first real driver back in Stage 8. Rather than defer or reorder stages, a minimal order-management slice was pulled into merchant-service first — the same move Stage 8 made for payment-service before Stage 9's Razorpay integration existed.

merchant-service publishes merchant.accepted, merchant.rejected, and order.ready — but onto order-events, not merchant-events. ADR 0009 says one topic per aggregate, not per producing service, and all three events describe a change to the order, not the merchant. order.ready's payload also carries the store's own lat/lng directly, taken from the merchant's own record at publish time — so delivery-service never needs a callback asking "where do I search," consistent with the "events carry enough data to act" rule Stage 8 established when it widened order.confirmed with userId.

DeliveryPartner has no lat/lng column at all. Identity, status, and task history live in Postgres; live coordinates live only in a single Redis key, delivery:partners:online, as a GEO set keyed by the partner's own row id — GEOADD via opsForGeo().add(), nearest-partner search via GEORADIUS-equivalent opsForGeo().radius(). A location ping is a high-frequency write that has no business touching a relational row every time; going offline is a ZREM on the same set, since GEO commands are sorted-set-backed under the hood.

DeliveryTaskStatus deliberately has no REJECTED state. When a partner declines, the task cycles back to PENDING_ASSIGNMENT, the rejecting partner's id is added to an excludedPartnerIds set on the task, and attemptAssignment re-runs immediately, searching again with that partner filtered out. The order still needs delivering — a rejection is a fact about one partner's declined offer, not a fact about the order — so a terminal status would have been the wrong model entirely, not just a missing feature.

If attemptAssignment's GEO search comes back empty, the task just sits at PENDING_ASSIGNMENT — no error, no dead end. A scheduled reaper (30s interval, the same pattern as Stage 5's reservation reaper) retries every task still in that state on every tick. Verified directly: took both test partners offline, marked an order ready (task sat unassigned, confirmed via the DB), brought a partner back online, and watched the next scheduled tick assign it with zero client action.

MerchantOrderService resolved "merchantId" as Merchant.getId() — the store application's own internal database primary key. But every other service that touches the concept — cart-service, order-service, catalog/inventory — treats "merchantId" as the store owner's userId, and that's exactly what the Kafka payload carried into MerchantOrderTask.merchantId. The two values are both real UUIDs, both plausible, and never equal. GET /pending silently returned [] — no exception, no log line, just the wrong empty answer — until a real order was placed and the endpoint actually queried against live data.

The first live reject call threw a 500: LazyInitializationException on excludedPartnerIds. JPA's @ElementCollection defaults to lazy, and DeliveryService deliberately has no @Transactional anywhere — the same no-transaction-in-orchestration doctrine OrderService has followed since Stage 8. By the time rejectAndReturnToQueue() tried to add to the set, the Hibernate session that loaded the entity was already closed. Fixed with FetchType.EAGER on that one small, bounded collection — the right call here, not a reason to break the no-transactions rule.

A Postgres column would have been simpler than standing up a whole Redis GEO key — why split the data across two stores for one entity?
Because the two pieces of data have completely different write patterns and completely different consumers. Identity and status change rarely — going online, accepting a task — and other services or an admin dashboard might reasonably want to query them relationally. Coordinates change constantly, on every location ping a partner's app sends, and the only thing that ever reads them is one operation: "who's near this point, right now." Writing every ping through Postgres would mean an UPDATE per ping for data nobody queries relationally anyway, and GEORADIUS on a Postgres column would need PostGIS or a hand-rolled bounding-box query to do what Redis GEO already does natively as a sorted-set operation. The split isn't extra complexity for its own sake — it's routing each kind of data to the store actually built for its access pattern.
Both values were named "merchantId" and both were valid UUIDs — how does a live test catch that when reading the code wouldn't?
Because the bug isn't a typo or a type error — every line individually compiles, every UUID is a real, well-formed UUID, and merchantService.getMine(ownerUserId).getId() reads as a completely reasonable way to answer "what's this merchant's id." The mistake is semantic: two different parts of the system independently, silently settled on two different definitions of what "merchantId" means, and nothing in the type system distinguishes a `UUID` that means "owner's userId" from a `UUID` that means "this application's internal PK." Reading either file alone, in isolation, the code looks correct. Only placing a real order, letting the real Kafka event populate a real row, and then querying that row through the code path that was supposedly wrong made the two values collide and the bug visible — which is exactly why this project's standing practice is to run each stage against the live stack rather than trust that idiomatic-looking code does what its name implies.
Wrapping DeliveryService.reject in @Transactional would have fixed the LazyInitializationException too — why reach for FetchType.EAGER on the entity instead?
Because the no-@Transactional-in-orchestration rule isn't incidental to this project — it's there specifically to avoid two proven failure classes: an external call (Kafka publish, another service's REST call) happening inside a transaction that might still roll back afterward, and Spring's self-invocation proxy trap silently no-op'ing a transaction boundary. Adding one exception "just for this method" reopens both risks for a collection that doesn't need a transaction at all to solve its actual problem — it needs to not be lazy. excludedPartnerIds is bounded by the number of delivery partners physically near one order, realistically a handful of UUIDs at most, so eager-loading it on every fetch of a DeliveryTask costs nothing meaningful and fixes the real defect (a lazy collection outliving its session) without touching a boundary the rest of the service deliberately keeps closed.
