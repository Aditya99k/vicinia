Why a registry instead of hardcoded URLs?
Instances move and scale; api-gateway resolves lb://SERVICE-NAME dynamically via client-side load balancing instead of every caller being redeployed when an instance changes.
What does disabling self-preservation trade away?
In prod it stops mass-evicting instances during what looks like a network partition. Locally it's off on purpose — a dev-speed tradeoff, not the production setting — so a restarted service is evicted in ~5s instead of a stale 90s lease.
Native vs. Git-backed config?
Git gives versioned history and works across machines; native (local files) is simpler for a single-VM zero-cost deploy. Either way consumers only see the HTTP contract, so the backend can be swapped later without touching them.
What if config-server is down at startup?
spring.config.import=optional:configserver:... — the optional: prefix means the service still starts, falling back to its own bundled config, instead of failing hard.
Why centralize routing/auth at a gateway?
One place for cross-cutting concerns — JWT validation, rate limiting, correlation IDs — instead of 16 services each reimplementing them. It's what lets the gateway inject a validated X-User-Id that every downstream service trusts.
Routes point at services that don't exist yet — broken?
No — lb://AUTH-SERVICE just 503s until AUTH-SERVICE registers. The path-prefix contract is decided once; each build stage makes the matching service real.
What decided Postgres vs. MongoDB per service?
State machines, money, or atomic-update-under-concurrency → Postgres (inventory, payment, coupons). Read-heavy, flexible-schema, low-consistency → Mongo (catalog, reviews).
"Each service owns its DB" — so why one shared instance?
Ownership is about schema/access boundaries, not physical servers. One instance costs ~250MB on a 12GB VM budget and avoids the cold-start autosuspend that managed free tiers impose.
How does that actually stop overselling?
One conditional UPDATE ... WHERE available_stock >= :qty, relying on Postgres's row lock — no distributed lock service, no new failure mode.
Why swap out Kafka + Zookeeper?
RAM. Kafka+ZK costs ~1.5–2GB; the free-tier VM was cut to 12GB total across 19 JVMs plus Postgres and Redis. Redpanda speaks the same Kafka wire protocol at a few hundred MB — same Spring Kafka client code either way.
What's the risk in that substitution?
Protocol compatibility isn't guaranteed 100% feature parity — worth validating schema registry and transactional-producer behavior before assuming zero risk, if those get used later.
Why one repo instead of one per service?
At 19 services for a single early build, it keeps shared BOM versions in one place and makes cross-service PRs atomic — worth revisiting once services have independent teams or release cadences.
Why commit an empty <modules/> at Stage 0?
That was the actual acceptance test for the stage — proving the parent's dependency management resolves cleanly before any service code depends on it, instead of discovering a bad BOM version three services in.
Why single-merchant-per-order?
Splitting multiplies delivery/payment/settlement complexity for a feature most real hyperlocal apps also avoid. (ADR 0001)
Why does order-service own canonical status instead of live-querying merchant/delivery?
Trades a few hundred ms of eventual consistency for one fast read instead of 3 network calls with 3 failure modes per page load. (ADR 0004)
Why RBAC as role+permission now, when V1 ships only 4 roles?
Adding a role later becomes a config change instead of a schema migration — the modeling cost is paid once, upfront. (ADR 0006)
