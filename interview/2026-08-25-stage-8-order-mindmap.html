Why it works

Stage 8's own "Done when" requires verifying checkout with wallet payment — but wallet debit/credit is payment-service's owned data, and that's Stage 9, not built yet. Every earlier stage's own dependencies already existed by the time that stage started; this was the first genuine sequencing conflict in the plan itself. Flagged directly and resolved with the user before any code: pull forward a minimal wallet-only payment-service now, real enough for genuine end-to-end verification, with Razorpay and the fuller ledger staying real Stage 9 scope.

cart (get + live-availability check) → coupon (optional, apply) → inventory (reserve → confirm or release) → payment (pay or fail). Full OrderStatus lifecycle from ARCHITECTURE.md §4.5, guarded by an OrderStatusTransition EnumMap — same pattern as Stage 3's MerchantStatusTransition, built for the complete graph through DELIVERED/REFUNDED even though this stage only drives CREATED through CONFIRMED/PAYMENT_FAILED/CANCELLED — MERCHANT_ACCEPTED onward has no real producer yet.

  • Reservation fails: two customers, one unit of stock, both carts independently showing available:true — fired both checkouts concurrently. One CONFIRMED, one genuinely hit inventory's 409 and correctly landed on CANCELLED, no oversell, loser never charged. A naive "add 999 to cart" doesn't reach this path at all — cart-service's own live check catches that earlier.
  • Payment fails: a $0-wallet customer reserved successfully, hit 402 on pay — order-service released the reservation and landed on PAYMENT_FAILED, stock confirmed restored.

A coupon-discounted order (20% capped, flat-10, both tested through the real checkout) charges the wallet the discounted total, not the subtotal. Cancelling that same order later refunds the exact amount actually charged — via order.cancelled published by order-service and consumed by payment-service (event-driven, per §8's REST-vs-Kafka rule — order-service doesn't need the refund's result to decide anything next). Re-cancelling, and cancelling a terminal PAYMENT_FAILED order, both correctly rejected as illegal transitions.

The very first happy-path test showed the customer's cart still full of items they'd just paid for. ARCHITECTURE.md §7 already names the fix — cart-service consuming order.confirmed — and Stage 6 explicitly deferred it since order-service didn't exist yet. It does now: order.created/order.confirmed payloads widened to carry userId (an async consumer needs enough to act, not a callback), and cart-service got its first Kafka dependency.

why latest, not earliest, this timeEvery prior read-model consumer (inventory's product cache, payment's wallet provisioning) used earliest to backfill real history. Here that would be wrong: a cart's contents today aren't what was in it when some old order was placed, and "catching up" on a stale confirmation could clear a cart full of unrelated newer items. Deliberately the Kafka default.

Wallet + WalletTransaction, auto-provisioned on user.registered (mirroring user-service's Stage 2 pattern), atomic debit via ADR 0002's pattern (a fourth instance of "same family as inventory" this project has now built), idempotent on (orderId, type) with the exact ON CONFLICT DO NOTHING fix already proven in Stage 7's coupon-service — caught and fixed in refundIfPaid before it ever ran, mirroring the same race shape.

A method this important, touching the database this many times — how is it correct with zero explicit transaction boundaries?
Because wrapping the whole flow in one transaction would be wrong, not just unnecessary — it would repeat Stage 5's Kafka-in-a-transaction bug in a new shape: a REST call to inventory-service that succeeds and mutates its database has no way to be undone if order-service's own transaction later rolls back for an unrelated reason, so the two services' states could permanently disagree. Each meaningful step here is exactly one orderRepository.save(...) call, and Spring Data's JpaRepository already wraps every individual method in its own transaction by default — so each step commits durably and immediately, before the next external call is ever made, without needing a single line of transaction-management code in this service at all. The correctness comes from never holding a commit open across a network call, not from careful annotation placement.
Wouldn't @Transactional on the small helper methods at least be harmless, even if unnecessary?
It would actually be worse than harmless — it would silently do nothing. Spring's @Transactional only works through a proxy Spring wraps around the bean; calling this.createOrder(...) from inside another method on the very same object skips that proxy entirely, a well-known Spring gotcha. An annotation that looks like a safety net but has zero effect is more dangerous than no annotation at all, because it invites false confidence. Relying on the repository's own built-in transactionality sidesteps the whole trap by never needing the proxy in the first place.
The obvious way to force a reservation failure is to order way more than the stock — why did that turn out to be the wrong test?
Because it never actually reaches inventory-service's reservation logic at all. Cart-service's own live-availability check (Stage 6) already flags any line where the requested quantity exceeds current stock, and order-service checks that flag before it ever calls reserve — so the request is rejected at the cart-validation step with a 409, several layers before the code path BUILD_TRACKER's "Done when" is actually asking about gets exercised. The only way to genuinely trigger inventory's own atomic-UPDATE-returns-zero-rows path is a real race: two requests that both pass the cart check honestly (because at the moment either checks, the stock genuinely was still sufficient), where only one can win the database-level decrement. Building the test scenario correctly required understanding the full call chain, not just picking an input that sounds like it should fail.
Cancel calls inventory-service directly but only publishes an event for payment-service — why the inconsistency?
It isn't inconsistent, it's each dependency getting exactly the mechanism §7's own table specifies. inventory-service was never listed as consuming order-events at all — the only way to release its reservation is the direct REST call it always exposed. payment-service, by contrast, is explicitly named as consuming order.cancelled to trigger a refund. §8's own rule for choosing REST versus Kafka is whether the caller needs the result to decide what happens next in the same request — and cancel's own outcome (the order becoming CANCELLED) never depends on whether the refund succeeds, since crediting money back essentially can't fail in a way order-service would need to react to. Two different dependencies, two different real requirements, two different correct mechanisms.
Every earlier stage made plenty of judgment calls independently — MongoDB vs. Atlas, the gateway public-paths fix, the ON CONFLICT rewrite. Why did this one need to be a question instead?
Scale of consequence. Those earlier calls were local and reversible — a config choice, a bug fix, an implementation detail that doesn't change what "Stage 4 is done" or "Stage 7 is done" means to someone tracking progress against the roadmap. Pulling Stage 9 work into Stage 8 changes the shape of two stages at once and reshapes what "done" means for both, in a way a later course-correction can't cleanly undo — Stage 9's remaining checklist now reads differently because of a decision made here. That combination — genuinely reshapes a shared plan, isn't obviously reversible, and the reasonable alternatives (stub the payment step, reorder the stages) are all real options a person might prefer differently — is exactly the situation worth one direct question rather than a silent judgment call.
