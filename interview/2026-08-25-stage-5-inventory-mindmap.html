Why it works

One row per (merchant, product) pair — merchantId correlates by value to the caller's own X-User-Id (same as merchant-service's own ownerUserId), productId to catalog-service's Mongo Product.id. Both cross-database correlations, not foreign keys — the same pattern user-service and merchant-service already established. productName/productCategory are a snapshot taken at creation time so listing reads never need a live call back to catalog-service.

why not a real Merchant.id foreign keyARCHITECTURE.md §7's dependency table lists catalog-service as inventory-service's only synchronous dependency — merchant-service isn't on that list. Resolving "which Merchant record does this caller own" would mean inventing an unlisted REST call. Treating the caller's own user id as the merchant identity avoids that entirely, and it's exactly the value merchant-service's own Merchant.ownerUserId already equals.

No distributed lock service. A single conditional UPDATE ... WHERE available_stock >= :qty, returning rows-affected instead of throwing — 0 means insufficient stock. Postgres's own row lock during the statement is the entire correctness mechanism. reserve decrements available/increments reserved; confirm (payment succeeded) decrements reserved permanently; release (failure/cancel/timeout) puts available back and drops reserved.

20 parallel reserve requests — each its own orderId, quantity 1 — fired at a listing with availableStock=1. Result: exactly one 201, nineteen 409s, final state availableStock=0 / reservedStock=1, exactly one reservation row in Postgres. Repeated against a second, independent listing with the identical result — not a one-off.

why the failed 19 don't leave any traceThe conditional UPDATE either affects one row or zero — a failed attempt never inserts a reservation row at all, so there's nothing to clean up. Correctness comes from never having created the wrong state in the first place, not from detecting and undoing it after the fact.
  • Re-reserve-ing an already-reserved (orderId, listingId) pair returns the existing row — no double-decrement. confirm/release on an order with nothing left PAYMENT_PENDING is a no-op ([]), not an error.
  • A scheduled job (default every 90s, configurable) finds reservations still PAYMENT_PENDING past a 15-minute timeout and releases them — DB-driven, not Redis TTL/keyspace-notify, since Redis expiry events aren't guaranteed delivery. Verified by backdating a reservation's reserved_at directly in Postgres and watching the next scheduled cycle release it and restore stock.

Every prior stage only produced events. ProductEventConsumer listens on product-events (group-id inventory-service, auto-offset-reset: earliest) and, since catalog-service's own event payload is deliberately thin — just a productId — does one REST fetch per product to populate a local KnownProduct cache. Listing creation checks that cache first, only falling back to a live catalog-service call on a miss. earliest meant this also backfilled both products approved back in Stage 4, before this service ever existed.

  • The earliest-offset backfill fires a REST call the instant the service starts, before the load-balanced RestTemplate's Eureka view of catalog-service has populated. Spring Kafka's near-instant default retry exhausted before that cache warmed up — both historical events were silently skipped. Confirmed via rpk group describe showing the consumer already past them; fixed with a 3s/8-attempt backoff, then replayed by resetting the consumer group's offset back to the start of the topic.
  • KafkaTemplate.send isn't covered by the JPA transaction. A multi-item reserve where line 1 succeeds and line 2 fails rolls the whole call back at the database level — but a stock-threshold event for line 1 had already been sent to Kafka before the exception fired, so the event survived even though the underlying change didn't. Caught by literally counting the topic's high-watermark before and after the exact rollback scenario. Fixed by deferring the publish to a post-commit callback.
Twenty requests hit the same row at once — what actually stops two of them from both reading "stock: 1" and both deciding they can proceed?
They never get the chance to read independently in the first place. An UPDATE ... WHERE statement isn't "read, then decide, then write" in application code — it's one atomic statement the database executes under a row lock. The first request's UPDATE takes the lock, checks the predicate against the current row, and commits its change. Every other concurrent request's UPDATE blocks on that same row until the lock releases, and only then evaluates its own WHERE available_stock >= 1 — against the now-already-decremented value. Nineteen of them see available_stock = 0 and correctly affect zero rows. No request ever acts on stale data, because no request ever gets to act until the database itself has finished the previous one. A Redis distributed lock would be solving a problem the database already solves for free, while adding a genuinely new failure mode (a lock that's never released after a crash, a TTL that doesn't match how long the operation actually takes) for zero additional correctness.
Every earlier stage published Kafka events from inside a @Transactional method with no problem — why did this one bite?
Because every earlier publish happened at the very end of a method that only ever succeeded or threw before making any change — merchant approval, product approval, and so on all published once, right before returning, with nothing left that could fail afterward and roll the whole thing back. inventory-service's reserve() is the first method in the project that does something meaningfully different: it loops over several line items, one database write per item, and can fail partway through, aborting a change that already happened earlier in the same call. The moment a Kafka publish sits in the middle of a transaction that might still roll back — rather than immediately before the method returns successfully — the two systems disagree about whether the enclosing operation actually happened. Kafka has no idea a Postgres transaction even exists; it commits the moment send() is called, regardless of what the database ends up deciding. The general rule this leaves behind: a side effect to a system the database transaction can't reach — a queue, a webhook, an external API call — belongs after the transaction is known to have committed, never in the middle of one that might still be undone.
Spring Kafka defaults new consumer groups to latest — why override that, and was it worth the startup-timing bug it caused?
Because latest would have been silently wrong for this specific case: catalog-service had already published product.created for two real products during Stage 4's own testing, before inventory-service — and this consumer group — existed at all. A consumer that only sees messages from the moment it first connects would permanently never learn about anything that happened before it existed, with no error and no obvious symptom beyond "the cache is just missing a couple of products for no visible reason." earliest is the only choice that makes a brand-new read-model consumer actually complete on its first boot. The cold-start REST-timing bug this exposed was a real bug worth fixing, but it was a consequence of doing the backfill immediately and synchronously inside the listener — not a reason to abandon backfilling in the first place.
Every other write endpoint in this project checks a specific permission — why do reserve/confirm/release just check InternalRequestFilter and nothing else?
Because they're not user actions at all — per ARCHITECTURE.md §8, this is the one place order-service will call inventory-service synchronously, and order-service doesn't exist until Stage 8. A permission check answers "is this specific person allowed to do this," which presumes a person is the caller in the first place; the actual caller here is another backend service acting on behalf of an order that's already been validated elsewhere. InternalRequestFilter already answers the only question that's actually being asked at this layer — "did this request come from inside the trusted system, not directly from the internet" — and that's the correct, complete boundary for an endpoint no human is ever meant to call directly.
